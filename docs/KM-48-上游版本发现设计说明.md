## 2. 关键实现裁决：为什么查询不走 `Manager.GetLatestVersion`

T3 的验收要求「永远分得清查到了和没查到」并记录真实查询时间。实现核查发现（v1.5.0，测试可复现）：上游对最新版本查询结果有**进程全局缓存**——`pkg/installer/providers/latest_cache.go` 的 `npmLatestVersionCache` 等（npm/pip/brew 同构），包名做键、TTL 5 分钟、**错误也缓存**（`shouldCacheLatestVersionError` 仅豁免 context 取消/超时），无任何失效入口。

后果：操作者点「检查更新」若经上游查询路径，一次网络故障后的 5 分钟内会把**陈旧的缓存错误**当新结果返回；反之，故障恢复后 5 分钟内仍报失败。「查不到」与「没查」被混为一谈，直接违反 spec 硬要求。因此按 KM-46 已确立的窄适配纪律收窄：

- **能力声明仍以上游 API 覆盖面为准**：`Manager.GetLatestVersion` 只支持 npm/pip/brew；native/binary 等明确返回 "version checking not supported"。codex 的来源清单（npm、brew、binary）与适用平台取自上游 catalog @v1.5.0（npm 包 `@openai/codex`，平台 darwin/linux/windows；brew cask `codex`，平台 darwin；binary 无安装命令，T1 判 BLOCKED）。
- **运行时查询由 `CommandQuerier` 以相同命令执行**：npm → `npm view <pkg> version`；brew → `brew info --json=v2 --cask <pkg>`（codex 是 cask，只解析 casks[].version；formula 语义在出现 formula 来源之前不实现，不留不可达分支）。结果永远新鲜，超时/取消沿 context 传播，错误分类只依据本层哨兵与 exec 类型化错误，不做错误文案匹配。

## 3. 模型与语义

### 3.1 检查结果三态（永远分得清）

- `ok`：查到了。携带 `version {raw, scheme}` 与 `queriedAt`（本次查询完成时间）。
- `failed`：没查到。携带 `failure {reason, detail, attempts}`；若该来源曾经成功过，附 `lastSuccess {version, queriedAt}`——**queriedAt 是缓存取得时间，不伪装成新查询**；从未成功过则缺省，前端必须显示「未知」，不得显示「最新」。
- `unsupported`：来源存在但上游不可查（binary 的上游缺陷；非默认渠道）。这是能力声明，不是查询失败——attempts=0，不发起查询。

`failure.reason` 分类：`query_failed`（命令非零退出，可重试）、`timeout`（超时）、`canceled`（调用方取消——「没人等它了」不是「查得太慢」，单独成类）、`source_unavailable`（npm/brew 不在本机 PATH，不重试——这本身就是要展示的适用性事实）、`version_parse_failed`（见 3.2）、`method_unsupported`、`channel_unsupported`。实际尝试次数只在结果层记录一次（`SourceResult.Attempts`），Failure 不重复携带。

### 3.2 版本：不假定 SemVer，不静默降级

上游 `agent.ParseVersion` 对垃圾输入静默返回 `{Raw: 输入}, nil`（KM-46 §4.3 已复核）。本服务不做二次信任，解释顺序：严格 SemVer（`semver`）→ 来源规则（`source_rule`，如 brew 修订段 `1.2.3_1`、日期式两段 `2024.11`）→ `unparsed`。scheme 显式随结果返回：

- `semver` 按 semver.org 优先级比较（含 prerelease 规则，build 元数据不参与）；
- `source_rule` 按确定性分段规则比较（数字段按数值、恒排于非数字段之前；缺段更小）；
- scheme 混用或 `unparsed` 参与比较 → `ErrIncomparable` 显式报错，不猜；
- `unparsed` 的发现结果**显式上报为 `version_parse_failed`**，不进成功缓存、不作为 ok 返回——上游的静默降级在这里终止。

### 3.3 超时与有限重试

单次查询默认 30s（`DefaultQueryTimeout`），总尝试默认 2 次（`DefaultMaxAttempts`），重试间隔 250ms；全部可配。仅 `query_failed`/`timeout` 重试；`source_unavailable`、解析失败、能力门拦截不重试。父 context 取消立即生效（不发起注定失败的查询）。

各来源**并发**查询（结果按声明顺序组装）：一次点击的总耗时上限收敛到单来源最坏预算（QueryTimeout×MaxAttempts+退避 ≈ 60s），不随来源数串行放大；这由各来源自身的超时与重试预算兜底，不另设全局超时旋钮。

## 5. API 与 T2 对齐状态

`POST /api/v1/agents/{agent}/upstream-versions/check`（挂在 `api/openapi/fleet-v1.yaml`，schemas 前缀 `Upstream*`）：一次点击返回全部来源的逐源记录。查询失败是报告的一部分（HTTP 200），不是传输层错误；只有未知 agent（404）与未装配服务（501）走 §6.4 错误体。

**T2 对齐**：T2（KM-47）正并行落地生命周期 proto/OpenAPI 契约。本端点先挂现有契约文件，路径与响应形状遵循仓库既有约定（动作动词后缀、错误模型、UTC RFC3339）；handler 只依赖 `internal.UpstreamDiscoveryAPI` 窄接口，T2 契约落地评审时由 T2 收编或更名，迁移不动实现。

**登记说明**：`/api/v1/agents` 是本单新启的资源命名空间，尚不在架构 v1.1.2 §8.1 的资源清单内——与 T2 对齐时一并登记（T2 的操作模型同样需要 agent 维度）；在此之前，命名空间的契约权威是本单的 fleet-v1.yaml 段落与设计说明，不在架构文档虚增条目。

## 6. 测试证据（受控版本源，`go test -race` 全绿）

覆盖验收要求的全部场景，全部用受控源（受控 npm 注册表替身 + fake brew 脚本 + 进程内 fake querier），未触真实上游与真实主机：

- 正常返回（SemVer 与非 SemVer 各一）；来源/渠道/包名/平台适用性/查询时间逐项断言
- 查询失败 → 失败原因 + 最近成功缓存及其**首次取得时间**（不伪装新查询）；从未成功 → 无缓存可回退
- 非 SemVer 可表达可比较（`1.2.3_1` > `1.2.2_9` 数值修订段等）；scheme 混用显式 incomparable
- 解析失败（`cheese`）显式上报 `version_parse_failed`，不进缓存、不降级为 ok
- 不支持的来源（binary）不发起查询、仍返回平台适用性；非默认渠道显式 unsupported
- 有限重试：可重试失败耗尽预算后报 timeout+attempts；`source_unavailable` 不重试；父 context 已死不发起查询
- 生产查询器端到端：fake npm `view` 全链路（含 `.fail-view` 注入）、fake brew exec 全链路
- HTTP 端点：未装配 501、未知 agent 404、报告透传（含逐源失败）、错误方法 JSON 404
- 隔离纪律：临时 HOME、PATH 首位放替身，查询只读，无安装/卸载路径（与 KM-46 同一约束）
- HTTP 端点错误映射：未知 agent 走 `ErrUnknownAgent` 哨兵 → 404；其余服务错误 → 500，绝不静默吞成 404

## 7. 边界与未验证项（如实声明）

- brew 查询在真实 macOS 上的行为**未验证**（能力矩阵 unverified）；本交付只证明对受控应答的处理正确。
- windows/amd64 + npm 维持 BLOCKED-PENDING-WINDOWS（上游 `.exe` 硬编码，待真机确认后另行决策）。
- 上游 catalog 未来变更（包名/平台）时，`capability.go` 的静态声明需同步更新——这是窄适配层的已知代价，换取不引入 catalog/viper 依赖面（与 KM-46 引擎同纪律）。
- 本单不授权在真实主机安装或卸载任何软件；查询只读上游，未触碰任何目标环境。
- **最近成功缓存是进程内的**（`Service.lastOK`）：服务重启后首次检查即失败时只能如实报「未知」——缓存不伪装持久记录。跨重启的结果留存在 T2 落地的操作/结果持久化模型里再收编，本单不引入存储层依赖。
- 「未知 ≠ 最新」的前端呈现归 T5（KM-50 验收项：查询失败展示失败原因与缓存时间）；本单交付的是可区分的 API 事实。
