## 统一适配契约

每个家族接入前记录：确切运行时来源及版本、可执行程序/版本探测方式、Linux/macOS/WSL 支持组合、可覆盖的安装方式、配置路径和格式、受管字段及所有权、健康检查方式。每项结论附版本对应的文档或 fixture 证据。截图不足以确定这些细节，当前均须在接入实现前验证。

对模型/provider 配置、MCP、Skills、rules 分别声明支持、明确不支持或尚未验证，并列出版本限制。能力声明随适配器/schema 版本登记，通过现有能力协商暴露给控制面；核心只读取声明，不硬编码各家族路径。不得为凑齐矩阵而虚构原生能力，无法满足的必需能力应记录为验收缺口并提交范围决策。

profile 显式请求未支持或未验证能力时，在 plan/预检阶段返回具体家族、能力及原因，禁止静默跳过或写入后才报成功。不包含该能力的 profile 可以继续管理其余已验证能力。凭据沿用既有不存储 secret 的边界，不能因新增家族把 token/登录文件纳入 Fleet 管理或备份。

保持共享 Adapter/reconciler 契约：Inventory 受管投影、同版本规范化、差异计划、原子应用、未托管内容保护、失败恢复与健康检查均不得绕过；daemon 和 SSH one-shot 行为一致。

## 逐家族验收

以下检查对八个家族分别记录结果，不能以 Codex/OpenCode 的示例替代其他家族：

1. 身份与兼容性：正确识别已安装/未安装、版本可解析/不可解析；记录支持的 OS 与版本，不兼容组合明确拒绝。
2. 配置与所有权：fixture 覆盖各已支持能力的渲染、读取、受管投影和未知字段保留；未验证/不支持能力在任何写入前拒绝。
3. 生命周期：安装/升级可验证，重复 reconcile 无实质变更，受管改动触发 drift，未托管改动不触发误报。
4. 恢复与一致性：失败恢复保留外部编辑，daemon 与 one-shot 复用相同行为与锁定契约；错误不伪装为 Reconciled。
5. 验收记录：家族、运行时来源、版本/OS、能力、fixture/测试证据、未通过原因逐项列明；没有证据的条目保留“未验证”。
