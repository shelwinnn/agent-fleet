## 1. 原始需求与成功标准

用户拥有 MacBook、Windows 台式机、Intel NUC 和多台 VPS，希望通过一个界面统一管理这些主机上的 AI agent 与 skill：安装、升级、卸载、探测新版本，以及一键升级，避免每次维护都在每台主机上重复操作。

用户进一步明确：Windows 台式机管理的是 **Windows 原生环境**，不能以 WSL 替代。MacBook 的芯片架构、NUC 的操作系统以及各 VPS 的系统与架构尚未提供，必须在接入时实际探测，不能由设备名称推断。

产品价值是：用户表达一次维护意图，系统在选定主机与用户环境中执行，验证实际结果，并展示逐机成功、失败和未知状态。允许一次性接入操作；接入后的正常维护不应要求逐台登录执行安装命令、手工填写当前最新版或预先复制 skill 缓存。

本次范围是软件与技能的生命周期管理。运行 agent 任务、同步聊天历史、远程交互终端、多人权限系统和任意主机配置管理，不属于这次纠偏的目标。

### 1.1 需求编号

| 编号 | 原始需求转化后的要求 | 完成证据 |
|---|---|---|
| R1 | 一个界面接入、查看并选择多台主机；明确 OS、架构、受管用户与执行环境 | 真机 inventory 与页面一致，Windows 原生明确标识 |
| R2 | 从界面安装指定 agent，并验证其确已安装在选定环境 | 空环境安装成功，版本与安装位置可核验 |
| R3 | 查询上游可用版本，展示已安装版本、可升级版本与查询时间 | 上游测试源出现新版本时，页面出现更新；查询失败不显示“已是最新” |
| R4 | 一次操作升级选定多台主机，固定此次目标版本并验证结果 | 多机真实升级，逐机结果与实际版本一致 |
| R5 | 从界面卸载 agent，明确保护配置、凭据和历史数据 | 程序已卸载，原有用户数据保留，失败可定位 |
| R6 | 从界面添加 skill 来源，在选定主机和 agent 中安装、发现更新、升级与卸载 | 来源解析、工件分发、目标目录与内容校验形成完整链路 |
| R7 | Windows 原生、macOS、Linux 均有完整生命周期支持 | 每个声明支持的 OS/架构/安装方式组合均有独立验收记录 |
| R8 | 离线、部分失败、结果丢失与重复点击都有可解释行为 | 不将未知计入成功，不重复执行同一操作，可只重试确定失败的目标 |

### 1.2 用户本次确认的约束

1. **agent 生命周期只操作程序本体。** 安装、升级和卸载均不修改、删除、迁移或重建用户数据。例如升级 Codex 只更新其程序本体，`~/.codex` 保持原样；卸载也不删除该目录。此要求不是可选择的“默认保留”，而是本次生命周期管理的硬边界。
2. **skill 操作参考 [runkids/skillshare](https://github.com/runkids/skillshare) 源码，由 Fleet 自行实现。** 用户在确认核心为 internal 包后明确选定此方式，替代此前 skillshare 优先 import 的要求。实现限定为本项目需要的来源解析、安装、更新检查、固定修订升级、目标同步及卸载。
3. **离线行为已确认。** 提交前离线的目标明确未执行，不在恢复联网后自动执行旧意图；已执行但结果未回传的目标保持未知，先核对结果再决定是否重试。
4. **agent 管理复用 [kevinelliott/agentmanager](https://github.com/kevinelliott/agentmanager)。** 优先 import；不重新编写同类发现、更新查询、安装、升级和卸载引擎。

agentmanager 的“优先 import”仍是技术选型约束，不等于上游已经存在满足全部要求的可导入接口。必须以源码确认包可见性、版本钉选、平台行为、执行副作用与许可证。skillshare 的 internal 限制已通过用户选择的源码参考实现路线解决选型问题，不再等待公共库提取、维护 fork 或 CLI 决策。

agent 数据保护与 skill 管理各自有操作边界：agent 生命周期不触碰 `~/.codex` 等数据目录；用户明确发起的 skill 操作可以通过 Fleet 的技能模块变更选定的受管技能目录或链接，不能顺带改动配置、凭据、会话或其他用户数据。

前端已确认的决定：页面面向用户任务，不承载与任务无关的工程说明，用户举例不构成固定词表；增加登录与退出代替管理 token 输入；一期不做用户管理；支持简体中文与英文且默认简体中文；登录细节与视觉布局分别确认。单操作者认证不意味着引入用户列表、注册、角色或权限管理。

## 4. 产品行为与架构边界

### 4.1 管理对象

最小执行目标是“主机 × OS 环境 × 用户 × agent 安装实例”。同一台机器的 Windows 原生与 WSL 是两个环境；同一用户的多个安装实例也不能靠 agent 名称合并。发现多个实例时，页面显示路径、来源和版本，要求选择本次目标。

首个范围建议为每个受管环境的一名用户、每个 agent 的一个明确安装实例、用户级安装。提升权限和系统级安装不默认执行；确需此能力时单独设计和授权。依赖缺失时明确报告缺少的运行时或权限，不能要求用户把本应由 Fleet 执行的 agent 安装再手工做一遍。

### 4.2 生命周期语义

| 行为 | 实际含义 | 验证要求 |
|---|---|---|
| 安装 | 目标实例应存在，版本固定为此次选择的版本 | 安装后重新发现实例并探测版本 |
| 升级 | 目标实例应存在，版本变为此次选择的版本 | 校验来源、环境、实际版本；命令退出成功不足以判定成功 |
| 卸载 | 明确要求目标实例不存在 | 按已识别安装来源执行卸载，确认目标实例已移除，并报告其他实例是否仍存在 |
| 停止管理 | 不再自动更改该实例 | 保留程序和数据，不显示为已卸载 |
| 卸载 skill | 移除选定 agent 的 Fleet 受管引用或副本 | 确认该目标不可再加载该受管 skill，保留其他 agent 使用的副本和用户自建内容 |

期望状态必须显式区分存在、缺席与停止管理；不能沿用“从快照省略即表示卸载”。界面操作转换为有版本的持久意图，再复用现有派发与验证机制，避免新增一套平行执行系统。

agent 的安装、升级、卸载和失败恢复均只针对程序本体，包括相应包文件和必要的程序入口，不修改配置、凭据、聊天历史、技能和用户项目。不得执行上游的用户数据清理选项；也不得借安装后的配置收敛或恢复步骤改写数据目录。安装脚本、版本探测与验证流程如果可能初始化或修改数据目录，必须先验证并限制副作用，不能仅凭“安装器不主动删除数据”判定合格。

修改或卸载前展示目标和影响并取得确认；重试同一已批准操作不重复询问，但影响变化时重新确认。卸载来源无法识别时拒绝变更并显示原因，不猜测删除可执行文件。数据清理不属于本需求，界面不提供与 agent 卸载捆绑的数据清空选项。

### 4.3 更新发现与固定部署

更新发现读取上游发布信息；drift 比较已安装状态与已批准期望状态。两者独立呈现，不能用“一致”代替“最新”。

页面展示已安装版本、目标版本、可用新版本、来源、适用平台、查询时间以及查询失败原因。建议首期支持手动“检查更新”，同时保留定期检查的扩展位置。原始需求没有要求无人值守自动安装；升级由用户触发。

“升级到新版本”在操作创建时解析为确定版本或 commit/digest，随后所有目标使用已固定内容。版本渠道规则随已验证来源登记，稳定版与预发布明确区分；不假定所有来源都使用 SemVer。不同平台没有相同可用版本时，预览明确列出不兼容目标，不能默默替换版本。

### 4.4 可复用模块与新增职责

| 模块 | 职责与外部使用方式 | 依赖与边界 |
|---|---|---|
| 机器台账与节点通道 | 登记目标环境、上报 inventory、派发操作和回传结果 | 复用现有主动连接与鉴权；原生 Windows 不强制依赖 SSH/WSL |
| 来源与版本解析 | agent 来源优先通过 agentmanager 查询；skill 来源由 Fleet 参考 skillshare 实现，输出候选与固定 revision/digest | Fleet 记录本次不可变意图；不默认上游更新接口支持精确版本，skill 更新以实际来源规则为准 |
| 节点生命周期执行 | 优先 import agentmanager；在受管用户环境执行 agent 安装升级卸载并验证结果 | Fleet 保留本地锁、操作记录、环境定位与数据保护；agent 操作不连带执行配置、MCP、rules 或 skill 收敛 |
| skill 管理模块 | Fleet 参考 skillshare 源码实现来源解析、安装、同步、更新检查、固定修订升级和卸载 | 接入现有缓存、适配器目录与操作流水线，明确唯一写入责任；不启用另一个同步引擎竞争写入 |
| 批量操作与界面 | 预览影响，固定版本，创建操作，展示逐机进展与结果 | 复用现有存储、Deployment 和 SSE；正常操作无需编辑 JSON |

能力声明应分别表示发现、查询更新、安装、升级、卸载，以及 skill 各生命周期能力。能够执行 `--version` 不能宣称整个 version 生命周期受支持。支持范围按 OS、架构、安装方式和验证证据记录。

### 4.5 上游复用核查与接入决策

核查记录见 [上游复用研究](2026-09-30-upstream-reuse-research.md)。研究固定了源码修订以保证可追溯，不表示这两个修订已获准成为生产依赖版本。

| 指定上游 | 已核查结论 | 对接入设计的约束 |
|---|---|---|
| skillshare | 核心逻辑位于 `internal/*`，模块为 `skillshare`，未提供对应公共库；从 Fleet 直接 import 核心能力受 Go 包可见性限制 | 用户已选择 Fleet 参考源码自行实现所需技能能力；上游源码作为设计与行为依据，跨主机派发和逐机结果仍由 Fleet 管理 |
| agentmanager | 有公开库可作为 import 候选，但查询、更新与卸载行为依赖具体 provider；当前公开操作不完整表达 Fleet 的固定目标版本与数据保护要求 | 逐方法验证版本钉选、Windows 原生路径/入口、输出与错误、数据副作用；不因存在 `Install`/`Update`/`Uninstall` 就宣称全部组合已满足需求 |

skillshare 接入方式已定：下一份技能子规格基于已固定的源码快照理解来源、同步、更新与卸载行为，再选择性实现本项目需要的流程。无需导入其 internal 包、维护完整 fork 或安装 skillshare CLI，也不将上游市场、TUI、插件管理等能力纳入本次范围。

实现时记录参考的上游文件与 commit。直接复制或改编 MIT 许可代码时，在相应代码或第三方许可记录中保留上游版权与许可声明；新引入依赖另行核查许可。行为参考不等于复制全部实现，尤其不能继承部分失败被计为成功、变更无关目标或未验证平台行为。

验收由 Fleet 的需求和数据保护边界决定，不要求完全兼容 skillshare CLI、磁盘格式或全部功能。保持固定 revision/digest、目标级所有权、逐项错误、重复操作幂等与三平台验证，复用 Fleet 已有工件与适配器基础。agentmanager 若有不符合数据保护的 provider，先限制支持范围；不可把用户数据边界降级来迁就上游。

### 4.6 数据流与错误处理

正常流程：界面选择目标 → 查询来源并固定版本 → 预检兼容性和影响 → 用户确认 → 创建带操作标识的持久意图 → 节点按实例加锁 → 执行 → 重新探测与校验 → 回传证据 → 页面显示逐机结果。

已确认的离线行为：离线目标明确显示“未执行：离线”，不自动在恢复联网后执行旧升级意图。用户重试时先核对原操作结果与当前状态；操作结果未知时先查询，禁止把连接中断当作失败并直接重复安装。

已经成功的目标不因其他目标失败而重新执行。相同请求标识复用已有操作；用户主动重试确定失败的目标生成可追溯的新操作，并重新预检。恢复旧期望状态不能直接保证软件版本回滚；不支持的恢复明确报出，不能只恢复配置后称软件已恢复。

外部请求和安装进程必须有超时、有限重试、退出码与输出记录；具体参数在各子规格中按来源确定。日志记录目标、版本、操作标识和时间，不记录 API Key、密码或 token。此类凭据按用户纪律存于节点 `.env`，控制面不上传或同步凭据值。

### 4.7 前端页面职责与交互

以下定义页面职责，不决定视觉布局、导航顺序或具体路由。沿用现有 Svelte 工程；各功能阶段同时交付后端能力与可用界面，不能只完成接口或禁用按钮。

| 页面/流程 | 必需内容与操作 | 关键状态 |
|---|---|---|
| 登录 | 按后续认证规格验证凭据，成功后进入控制面 | 未登录、提交中、凭据错误、服务不可达；不要求输入或复制管理 token |
| 总览 | 主机在线情况、可用更新、最近操作及需要处理的失败 | 加载、空数据、连接中断；状态解释面向用户，不展示 SSE 协议或错误堆栈 |
| 主机列表与详情 | OS/架构、受管用户、连接状态、已安装 agent/skill；选择目标主机和进入管理操作 | 在线、离线、信息过期、读取失败；平台不支持的原因使用产品语言 |
| Agent 管理 | 已安装/可升级版本、安装来源和目标；安装、检查更新、批量升级、卸载 | 可更新、已完成检查、查询失败、操作中、部分成功、未知；卸载明确保留数据 |
| Skill 管理 | 添加来源、查看修订、选择主机与 agent；安装、检查更新、升级和卸载 | 解析中、更新可用、来源不可达、目标冲突、逐目标结果；确认作用范围 |
| 操作记录与详情 | 操作目标、固定版本/revision、逐机进度、结果、失败原因和可重试目标 | 执行中、成功、失败、未执行、结果待确认；失败原因可行动，不直接输出内部错误体 |
| 退出与语言切换 | 全局可到达的退出及中英文切换入口 | 退出后结束本浏览器会话；语言切换不改变操作目标或重复提交操作 |

既有 Profiles、发布和 SSH 视图是否独立保留、如何组织导航，在功能及布局规格中决定。本轮不删除既有能力；所有保留视图同样受文案和 i18n 约束，普通生命周期操作不以编辑 JSON 为前提。

安装、升级、卸载交互：选择主机和实例 → 选择版本或来源 → 预检并展示影响 → 用户确认 → 展示逐目标结果。未检查到最新版本时不显示“已是最新”；离线目标显示未执行；未知结果先查询证据，不能直接提供会造成重复执行的重试。

### 4.8 页面文案边界

**原则：页面表达用户能理解、与当前任务有关的信息，不把研发过程当作产品内容。** 是否保留一项文字，取决于它的用途和呈现位置，不取决于是否包含某个词、编号、路径或技术名词。用户截图中的文字是问题示例，不是完整禁止清单。

每项可见信息至少服务于一个明确目的：识别正在管理的对象；理解真实状态及信息是否新鲜；比较版本或来源并作选择；判断变更范围、数据影响或实际风险；知道可执行的下一步；定位本次操作的问题。如果内容只帮助开发者解释系统如何实现、依据哪份设计或完成哪个开发任务，应留在工程文档和日志中。

以下是**非穷尽的工程说明类型**，用于识别同类问题，而非逐字匹配的黑名单：

| 类型 | 可能的表现 | 处理依据 |
|---|---|---|
| 设计依据与追溯 | ADR/FR/任务编号、契约文件、评审结论、设计章节引用 | 用户无需查阅开发依据才能使用功能；呈现对用户有影响的实际行为 |
| 内部实现解释 | 状态机、schema、generation、控制器归属、消息协议、数据库结构 | 保留实际对象与状态，移除无助于用户操作的实现细节 |
| 开发进度与交付过程 | 切片/批次已合入、接口尚未注册、后续某任务完成、工程“当前限制”清单 | 不把研发路线放进操作界面；确实影响当前操作的可用性用业务原因说明 |
| 调试信息直出 | 堆栈、原始异常、内部枚举、请求/响应 dump、重试计数与协议日志 | 先表达发生了什么及用户能做什么；必要定位信息应有明确用途，不能用日志替代错误说明 |
| 开发占位与测试痕迹 | TODO、stub/mock/fixture 标记、测试断言说明、无意义的演示备注 | 未交付能力不伪装可用；空状态提供用户下一步，测试依据留在测试记录 |
| 实现自证与维护注释 | “不提供假入口”“按某契约禁用”“为满足验收保留”“由某控制器维护” | 实现正确性由验证保证，页面不向用户解释研发人员如何遵守规则 |
| 内部模型的无解释投射 | 数据结构字段名、布尔值、机器错误码直接作为标签 | 用用户能理解的含义表达；真正需要编辑的配置字段可保留，并给出必要解释 |

例如，截图中的契约路径、FR 状态设计说明和未实现端点清单不帮助用户管理主机，应移出页面。实际状态仍保留并转为可行动文案，如“状态待确认”“主机离线，暂时无法升级”“连接中断，正在重试”。即使换成未被列举的新缩写或开发说明，也按同一原则处理。

能力尚未交付时不展示研发占位；已有功能因离线、权限、安装方式不支持或操作冲突不可用时，可以禁用并解释实际原因。影响用户决策的限制和风险必须如实说明，不能因文案清理而隐藏失败、掩盖风险或把未知显示为成功。

技术信息并非一律删除：agent 品牌与版本、Git 来源/revision、安装路径、用户需要设置的服务地址，以及用于定位当前失败的操作标识，都可能直接服务于任务。地址作为用户配置项有价值，地址作为“后端某端点尚未实现”的研发说明没有价值；同类信息须结合用途判断，不能统一屏蔽路径、编号、接口或专业术语。

此原则覆盖正文、侧栏、卡片、工具提示、弹窗、空状态、错误、按钮和可访问性标签，不能把无关工程说明从正文移到 tooltip。后端业务错误映射为本地化产品文案；开发日志不直接成为默认错误内容。

### 4.9 登录、退出与认证边界

一期要求：验证登录凭据，成功签发 token；浏览器凭该 token 访问受保护操作，提供退出入口；去除手工管理 token 的用户流程。认证必须由服务端验证，不能只做前端页面跳转。登录失败不获得 token，未登录/失效 token 不能访问受保护数据或执行维护；实时更新连接遵循同一认证状态。

退出后清除本浏览器的认证状态、停止受保护的数据与实时连接，并回到登录页。退出不取消已由用户确认的节点操作，也不将其结果误报为失败。服务端是否立即撤销已签发 token，需要在认证子规格中明确，当前不假定已实现。

用户管理不进入一期：不做注册、用户 CRUD、多用户角色、RBAC 或管理后台。登录凭据来源、是否采用单账户用户名/密码、token 格式和有效期、浏览器存储方式、刷新策略、失效处理与服务端退出语义，单独确认后写认证规格。不要把现有长期管理 token 改名为密码来代替登录设计，也不预先认定使用 JWT。

凭据和签名秘密按用户纪律放在 `.env`，不写进代码、文档、前端构建产物或日志。现有 API 脚本调用的兼容策略在认证规格中一并确定，不因新增浏览器登录擅自取消已经授权的非浏览器访问。

### 4.10 i18n 与视觉设计边界

引入集中管理的 i18n 消息资源，一期提供 `zh-CN` 和 `en`，首次进入默认 `zh-CN`。导航、页面标题、按钮、表单验证、确认弹窗、空/加载/禁用状态、通知、业务错误和可访问性标签均按所选语言呈现；日期、相对时间、数字和数量文案也遵循 locale，不能只翻译静态导航。

不翻译品牌、版本号、用户提供的数据、来源地址和操作标识。语言切换覆盖当前页面以及后续弹窗、实时消息与错误；未完成翻译的 key 不直接显示到页面，也不以中文页面夹杂英文自然语言作为交付。具体 i18n 库、语言偏好保存方式在前端功能规格中确定。

风格与布局重构由用户另开会话确认。本文不预设配色、字体、间距、表格/卡片样式或侧栏方案；本会话完成文案、认证、i18n 与功能边界记录，后续视觉方案必须满足这些约束。

## 5. 开发顺序与阶段退出条件

以下是建议路线，不是已批准的实施计划。默认首个 agent 候选为 Codex，因为已有可复用适配器；最终选择由用户评审决定，不影响 R1–R12。不按 agent 数量或旧 FR 完成比例衡量阶段成功。

| 阶段 | 交付内容与依赖 | 退出条件 | 对应需求/缺口/验收 |
|---|---|---|---|
| S0 纠偏定案与接入核查 | 核查 agentmanager import、精确版本与副作用；落实 skillshare 源码参考实现范围与许可；确认首个 agent、受管用户与实际平台；获批后同步旧文档冲突口径 | agent 公共库与 skill 源码参考范围有明确依据；未解决数据保护/版本语义问题不进入生产接入 | R1–R8；G1、交付口径冲突；A0、A10 |
| S1 一个 agent 完整闭环 | 优先 import agentmanager；接入实际 Windows 原生、macOS、Linux 环境；逐平台打通同一 agent 的发现、安装、更新查询、升级、卸载与 UI 操作 | 三种环境各有成功证据，所有 agent 生命周期操作的数据目录保持不变，未完成组合明确标为不支持/未验证 | R1–R5、R7；G1–G4、G7；A1–A5、A10 |
| S2 一个 skill 完整闭环 | 参考 skillshare 源码，在 Fleet 内实现来源解析、安装同步、更新发现、固定修订升级与卸载；在 S1 的 agent 上验收，不要求节点预填缓存 | 同一来源可跨主机安装与更新，目标和所有权准确，缺失/损坏内容明确失败，现有与新增逻辑没有竞争写入 | R6、R7；G5；A6、A10 |
| S3 多主机可靠批量维护 | 将前两阶段用于用户实际 NUC 和多台 VPS；补批量操作、部分失败、离线、去重与结果查询 | 正常批量操作和失败场景均有逐机证据，不要求逐台手工维护 | R4、R8；G6、G8；A7–A9 |
| S4 扩展覆盖与配置能力 | 前三阶段通过后，再扩展其他 agent、更多安装方式和平台组合；按真实使用频率推进 MCP、rules、模型配置与高级发布策略 | 每个新增组合复用相同验收要求，不以名称出现在矩阵中替代验证 | R2–R8；重复 A1–A10 中适用场景 |

NUC 的系统如果不是首期 Linux，按实际系统纳入平台验证，不能把它自动算作 Linux 通过。多台 VPS 应使用真实目标进行最终验收；容器和 loopback 可作为开发测试，不替代真实设备证据。

每个阶段均先编写限定范围的子规格，完成评审，再写实施计划。S1 是首份 agent 生命周期实施计划的范围；S2–S4 为路线，认证与前端基础分别形成限定范围的规格和计划，不能据此提前修改无关模块。保持单控制面与既有可靠性机制，不为纠偏新增微服务、通用包管理平台或完整插件市场。

前端交付顺序补充：先按 R9/R11 清理产品文案并建立中英文资源；登录与退出按独立认证规格推进，作为日常使用的基础；Agent、Skill 和操作结果页面分别随 S1–S3 的后端闭环交付，并满足 A11–A14。登录细节未确认前不实现猜测的认证协议，视觉布局未确认前不进行风格重构。这两项独立确认不阻碍记录页面职责和产品文案要求。

## 6. 验收场景

所有场景在本文件创建及本次修订时均为 **未执行**。场景中的版本与 revision 是测试符号，不代表当前上游最新版；执行时选取真实来源存在的精确值并记录。发现更新的自动化测试使用可控发布源；正式支持来源必须另有真实查询和安装证据。

| 编号 | 前置与操作 | 必须观察到的结果 |
|---|---|---|
| A0 范围一致 | 对照原始需求评审文档与支持矩阵 | Windows 原生列入目标；缺失能力如实记录；“已交付”不能包含未执行验收 |
| A1 真机接入与发现 | 接入 Windows 原生、MacBook 和一台 Linux 主机；包含已安装和未安装环境 | 正确报告 OS/架构/用户、agent 安装状态、路径、来源和版本；Windows 的进程与路径属于原生环境 |
| A2 界面安装与幂等 | 在三种环境各选择未安装的目标，预置可校验的数据目录，从界面安装固定 V1；重复提交同一请求 | 实际安装 V1，目标用户可调用；已有数据目录的路径、文件内容、权限和链接保持；重复请求复用操作，不重复安装；运行时或权限缺失时有明确错误 |
| A3 新版本发现 | 上游测试源最初只有 V1，随后发布适用的 V2；点击检查更新；再模拟查询失败 | 页面从无更新变为显示 V2；失败显示未知/失败及时间，保留缓存时间，不称已是最新；不自动安装 |
| A4 多平台升级 | 选定三种环境，将 V1 升级到 V2；预置 `~/.codex` 或该平台实际数据目录的配置、凭据、会话和 skill fixture；操作途中上游出现 V3 | 本次目标仍为 V2；逐机实际版本为 V2；数据目录路径、文件内容、权限和链接保持；其他实例不被误升级；命令成功但版本未变必须判失败 |
| A5 卸载与停止管理 | 给 agent 准备可校验的用户数据；先停止管理，再重新纳管并明确卸载 | 停止管理后程序仍在；明确卸载后目标实例不存在；配置、凭据和历史数据保持；安装来源不明则拒绝变更 |
