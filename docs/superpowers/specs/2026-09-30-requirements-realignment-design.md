## 1. 原始需求与成功标准

用户拥有 MacBook、Windows 台式机、Intel NUC 和多台 VPS，希望通过一个界面统一管理这些主机上的 AI agent 与 skill：安装、升级、卸载、探测新版本，以及一键升级，避免每次维护都在每台主机上重复操作。

用户进一步明确：Windows 台式机管理的是 **Windows 原生环境**，不能以 WSL 替代。MacBook 的芯片架构、NUC 的操作系统以及各 VPS 的系统与架构尚未提供，必须在接入时实际探测，不能由设备名称推断。

产品价值是：用户表达一次维护意图，系统在选定主机与用户环境中执行，验证实际结果，并展示逐机成功、失败和未知状态。允许一次性接入操作；接入后的正常维护不应要求逐台登录执行安装命令、手工填写当前最新版或预先复制 skill 缓存。

本次范围是软件与技能的生命周期管理。运行 agent 任务、同步聊天历史、远程交互终端、多人权限系统和任意主机配置管理，不属于这次纠偏的目标。

### 1.1 需求编号

| 编号 | 原始需求转化后的要求 | 完成证据 |
|---|---|---|
| R1 | 一个界面接入、查看并选择多台主机；明确 OS、架构、受管用户与执行环境 | 真机 inventory 与页面一致，Windows 原生明确标识 |
| R2 | 从界面安装指定 agent，并验证其确已安装在选定环境 | 空环境安装成功，版本与安装位置可核验 |

| R4 | 一次操作升级选定多台主机，固定此次目标版本并验证结果 | 多机真实升级，逐机结果与实际版本一致 |

## 3. 方案比较与推荐

| 方案 | 做法 | 收益 | 代价与限制 |
|---|---|---|---|
| A 保留底座，按使用场景补齐生命周期（推荐） | 复用控制面、节点连接、适配器、执行流水线、结果存储；补更新查询、安装升级卸载和 skill 分发 | 直接解决重复维护，保留已投入的可靠性机制 | 需要修正期望状态和能力声明，补跨平台实现与真机验证 |
| B 先改成批量命令工具 | 从页面发安装与卸载命令，逐机收集退出结果 | 首个命令执行路径较短 | 仍要补环境识别、版本验证、幂等与 skill 分发；容易把复杂度转移给操作者 |
| C 重写为新系统 | 替换控制面、协议、执行模型和界面 | 可重新选择所有技术方案 | 当前证据不足以证明现有底座阻塞目标，会重复已有工作并延后核心价值 |

建议采用 A。首个闭环只覆盖一个 agent 与一种明确安装方式在实际设备上的组合，随后打通一个 skill，再扩展主机与 agent 覆盖范围。后续阶段分别编写子规格和实施计划，不把整个路线一次性变成巨型实施任务。

## 4. 产品行为与架构边界

### 4.1 管理对象

最小执行目标是“主机 × OS 环境 × 用户 × agent 安装实例”。同一台机器的 Windows 原生与 WSL 是两个环境；同一用户的多个安装实例也不能靠 agent 名称合并。发现多个实例时，页面显示路径、来源和版本，要求选择本次目标。

首个范围建议为每个受管环境的一名用户、每个 agent 的一个明确安装实例、用户级安装。提升权限和系统级安装不默认执行；确需此能力时单独设计和授权。依赖缺失时明确报告缺少的运行时或权限，不能要求用户把本应由 Fleet 执行的 agent 安装再手工做一遍。

### 4.2 生命周期语义

| 行为 | 实际含义 | 验证要求 |
|---|---|---|
| 安装 | 目标实例应存在，版本固定为此次选择的版本 | 安装后重新发现实例并探测版本 |
| 升级 | 目标实例应存在，版本变为此次选择的版本 | 校验来源、环境、实际版本；命令退出成功不足以判定成功 |
| 卸载 | 明确要求目标实例不存在 | 按已识别安装来源执行卸载，确认目标实例已移除，并报告其他实例是否仍存在 |
| 停止管理 | 不再自动更改该实例 | 保留程序和数据，不显示为已卸载 |
| 卸载 skill | 移除选定 agent 的 Fleet 受管引用或副本 | 确认该目标不可再加载该受管 skill，保留其他 agent 使用的副本和用户自建内容 |

期望状态必须显式区分存在、缺席与停止管理；不能沿用“从快照省略即表示卸载”。界面操作转换为有版本的持久意图，再复用现有派发与验证机制，避免新增一套平行执行系统。

卸载默认保留 agent 配置、凭据、聊天历史与用户项目。清空这些数据不进入首个闭环。修改或卸载前展示目标和影响并取得确认；重试同一已批准操作不重复询问，但影响变化时重新确认。卸载来源无法识别时拒绝变更并显示原因，不猜测删除可执行文件。

### 4.3 更新发现与固定部署

更新发现读取上游发布信息；drift 比较已安装状态与已批准期望状态。两者独立呈现，不能用“一致”代替“最新”。

页面展示已安装版本、目标版本、可用新版本、来源、适用平台、查询时间以及查询失败原因。建议首期支持手动“检查更新”，同时保留定期检查的扩展位置。原始需求没有要求无人值守自动安装；升级由用户触发。

“升级到新版本”在操作创建时解析为确定版本或 commit/digest，随后所有目标使用已固定内容。版本渠道规则随已验证来源登记，稳定版与预发布明确区分；不假定所有来源都使用 SemVer。不同平台没有相同可用版本时，预览明确列出不兼容目标，不能默默替换版本。

### 4.4 可复用模块与新增职责

| 模块 | 职责与外部使用方式 | 依赖与边界 |
|---|---|---|
| 机器台账与节点通道 | 登记目标环境、上报 inventory、派发操作和回传结果 | 复用现有主动连接与鉴权；原生 Windows 不强制依赖 SSH/WSL |
| 来源与版本解析 | 按 agent 或 skill 来源查询发布，返回候选与不可变目标 | 使用来源特定规则和受限网络请求；不负责安装 |
| 节点生命周期执行 | 接收明确目标，发现实例，计划、执行、验证安装升级卸载 | 复用本地锁、operation 和 adapter；路径、安装方式与进程调用按平台实现 |
| skill 工件链路 | 解析来源，生成不可变工件，传输、校验并在选定 agent 物化 | 复用缓存设计与适配目录；软链不可用时采用经过验证的复制模式 |
| 批量操作与界面 | 预览影响，固定版本，创建操作，展示逐机进展与结果 | 复用现有存储、Deployment 和 SSE；正常操作无需编辑 JSON |

能力声明应分别表示发现、查询更新、安装、升级、卸载，以及 skill 各生命周期能力。能够执行 `--version` 不能宣称整个 version 生命周期受支持。支持范围按 OS、架构、安装方式和验证证据记录。

### 4.5 数据流与错误处理

正常流程：界面选择目标 → 查询来源并固定版本 → 预检兼容性和影响 → 用户确认 → 创建带操作标识的持久意图 → 节点按实例加锁 → 执行 → 重新探测与校验 → 回传证据 → 页面显示逐机结果。

建议首期离线目标明确显示“未执行：离线”，不自动在恢复联网后执行旧升级意图。用户重试时先核对原操作结果与当前状态；操作结果未知时先查询，禁止把连接中断当作失败并直接重复安装。

已经成功的目标不因其他目标失败而重新执行。相同请求标识复用已有操作；用户主动重试确定失败的目标生成可追溯的新操作，并重新预检。恢复旧期望状态不能直接保证软件版本回滚；不支持的恢复明确报出，不能只恢复配置后称软件已恢复。

外部请求和安装进程必须有超时、有限重试、退出码与输出记录；具体参数在各子规格中按来源确定。日志记录目标、版本、操作标识和时间，不记录 API Key、密码或 token。此类凭据按用户纪律存于节点 `.env`，控制面不上传或同步凭据值。

## 5. 开发顺序与阶段退出条件

以下是建议路线，不是已批准的实施计划。默认首个 agent 候选为 Codex，因为已有可复用适配器；最终选择由用户评审决定，不影响 R1–R8。不按 agent 数量或旧 FR 完成比例衡量阶段成功。

| 阶段 | 交付内容与依赖 | 退出条件 | 对应需求/缺口/验收 |
|---|---|---|---|
| S0 纠偏定案 | 评审本文，确认首个 agent、受管用户与实际平台；获批后同步 README、需求和支持矩阵中的冲突表述 | 原始需求、当前能力与建议路线分开记录，Windows 原生不被排除 | R1–R8；G1、交付口径冲突；A0 |
| S1 一个 agent 完整闭环 | 接入实际 Windows 原生、macOS、Linux 环境；逐平台打通同一 agent 的发现、安装、更新查询、升级、卸载与 UI 操作；平台适配和执行实现一起交付 | 三种环境各有成功证据，任何未完成组合明确标为不支持/未验证 | R1–R5、R7；G1–G4、G7；A1–A5 |
| S2 一个 skill 完整闭环 | 在 S1 的 agent 上打通来源解析、分发、物化、更新发现、升级与卸载；不要求节点预填缓存 | 同一来源可跨主机安装与更新，卸载保护非受管内容；缺失或损坏工件明确失败 | R6、R7；G5；A6 |
| S3 多主机可靠批量维护 | 将前两阶段用于用户实际 NUC 和多台 VPS；补批量操作、部分失败、离线、去重与结果查询 | 正常批量操作和失败场景均有逐机证据，不要求逐台手工维护 | R4、R8；G6、G8；A7–A9 |
| S4 扩展覆盖与配置能力 | 前三阶段通过后，再扩展其他 agent、更多安装方式和平台组合；按真实使用频率推进 MCP、rules、模型配置与高级发布策略 | 每个新增组合复用相同验收要求，不以名称出现在矩阵中替代验证 | R2–R8；重复 A1–A9 中适用场景 |

NUC 的系统如果不是首期 Linux，按实际系统纳入平台验证，不能把它自动算作 Linux 通过。多台 VPS 应使用真实目标进行最终验收；容器和 loopback 可作为开发测试，不替代真实设备证据。

每个阶段均先编写限定范围的子规格，完成评审，再写实施计划。S1 是下一份实施计划的范围；S2–S4 为路线，不能据此提前修改无关模块。保持单控制面与既有可靠性机制，不为纠偏新增微服务、通用包管理平台或完整插件市场。

## 6. 验收场景

所有场景在本文件创建时均为 **未执行**。A1–A9 的版本与 revision 是测试符号，不代表当前上游最新版；执行时选取真实来源存在的精确值并记录。发现更新的自动化测试使用可控发布源；正式支持来源必须另有真实查询和安装证据。

| 编号 | 前置与操作 | 必须观察到的结果 |
|---|---|---|
| A0 范围一致 | 对照原始需求评审文档与支持矩阵 | Windows 原生列入目标；缺失能力如实记录；“已交付”不能包含未执行验收 |
| A1 真机接入与发现 | 接入 Windows 原生、MacBook 和一台 Linux 主机；包含已安装和未安装环境 | 正确报告 OS/架构/用户、agent 安装状态、路径、来源和版本；Windows 的进程与路径属于原生环境 |
| A2 界面安装与幂等 | 在三种环境各选择未安装的目标，从界面安装固定 V1；重复提交同一请求 | 实际安装 V1，目标用户可调用；重复请求复用操作，不重复安装；运行时或权限缺失时有明确错误 |
| A3 新版本发现 | 上游测试源最初只有 V1，随后发布适用的 V2；点击检查更新；再模拟查询失败 | 页面从无更新变为显示 V2；失败显示未知/失败及时间，保留缓存时间，不称已是最新；不自动安装 |
| A4 多平台升级 | 选定三种环境，将 V1 升级到 V2；操作途中上游出现 V3 | 本次目标仍为 V2；逐机安装后实际版本为 V2；其他实例不被误升级；命令成功但版本未变必须判失败 |
| A5 卸载与停止管理 | 给 agent 准备可校验的用户数据；先停止管理，再重新纳管并明确卸载 | 停止管理后程序仍在；明确卸载后目标实例不存在；配置、凭据和历史数据保持；安装来源不明则拒绝变更 |
| A6 skill 生命周期 | 从同一 Git 来源解析 revision C1，在三种环境安装至选定 agent；发布 C2 后检查更新、升级；最后卸载一处 | 无需预填节点缓存；内容 digest 与目标一致；更新固定 C2；卸载仅移除该处受管内容，其他引用与用户自建目录不受影响 |
