## 第一性原理审核：agent-fleet 架构设计文档

审核对象：《agent-fleet MVP 架构设计文档》v1.0（1185 行）；需求基准：spec v0.1（1981 行）。审核方式：以系统必须成立的性质为起点逐条对照文档，而非按 spec 章节核对文档是否"写了"。两文档均已完整读完，本次为纯文档层审核，**未运行任何代码、未做任何实测**，文中的性能数字均转引 spec 原文，不构成本次验证结论。

### 结论

设计的骨架是对的：从"期望状态 → 快照 → 双通道派发 → 本地收敛 → 观测比对"这条闭环推出来的六个选择（单进程、SQLite、出站 gRPC、系统 OpenSSH、单一 reconciler、无 secret 分发）都能从需求直接推出，不是套用模式；不变量 I-1～I-7、护栏 12 条的落点、安全 14 条的逐条归属都成立，可追溯性总表无缺章。

但有一个**结构性缺口**贯穿全文：文档把三种语义不同的摘要当成一种混用，而整个产品的两条承诺（"是否 drift"和"回滚到第 N 代"）都建立在这个未定义清楚的契约上。这不是措辞问题，是设计缺口——补它需要新增一个"期望侧受管投影摘要"的产物、它在快照里的位置，以及规范化规则的版本化传递路径，属于要改设计的范畴。其余发现按同一标准（能否从需求推出、失效时会不会静默）分三档列出。

### 必须先修（会让已承诺的保证静默失效）

**M1｜三种摘要被当成一种，comparison 契约缺失。**
文档中实际出现三个不同摘要：全量快照摘要（§4.8，"对快照规范化 JSON"算 SHA-256）、期望侧受管投影摘要（FR-10.3 与 §4.4 直接写"观测受管摘要 == 期望摘要"）、观测侧受管投影摘要（§5.5、§7.1，只对受管字段投影算）。spec §10.2 只说观测摘要对 normalized managed state 计算，§21.3 却要求它等于 desired digest——期望侧的投影摘要**spec 没定义，文档也没补**。

后果具体：控制面若用快照摘要去比，节点永远不等（未托管字段、schema 版本、协议字段都在里面），系统会永久显示 drift；若节点上报全文件哈希去比，任何无关编辑都误报；只有两边都按同一规范化规则在同一字段集上投影，比较才有意义。而文档明确禁止控制面 import 任何适配器包（I-1、护栏 #2），所以"期望侧投影"只能由快照携带的 adapter schema 描述符加上一套规范化规则算出来，且该描述符与规则版本必须随 generation 一起落进快照、随 bundle 与 gRPC 下发——文档没有这一项，也没有把它写进 §6.3 的快照结构。

**建议**：在 §6.3 快照里新增两个显式字段（如 `projectionSchema`：适配器投影字段描述符 + `canonicalizationVersion`），在 §7.1 画清五个产物各自覆盖什么、由谁算，并明确**唯一权威判据是"期望投影摘要 vs 观测投影摘要"**，全量快照摘要只用于 generation 内容寻址与快照身份，两者不得互相比较。

**M2｜drift 判据在文档内部互相矛盾。**
§4.2 与 §4.4 按摘要判定（"观测摘要 ≠ 期望摘要"），§7.1 却按字段投影逐字段比较（"normalize(观测投影) vs normalize(期望投影映射到该适配器受管 schema)"），FR-8.3 又写回摘要式。两种判据在规范化与字段集不一致时结论会不同。必须指定一个是权威、另一个只是 UI 诊断（推荐摘要做判据、逐字段 diff 只做展示），否则实现者会各写一套，验收 G 的"drift 可一键收敛"在边界场景下不可复现。

**M3｜回滚依赖快照保留，但保留契约没定义。**
§6.3 说"回滚 = 将机器重指向前一快照 generation"，§10.1 说 `desired_snapshots` 同 machine+digest 唯一。这两条要在磁盘增长下同时成立，必须额外保证：旧 generation 的快照永不回收，或回收后回滚要返回一个明确的失败态。文档只在 §10.3 对 Skill 工件提了引用计数清理，对快照只字未提。若为了控制磁盘清掉旧快照，验收 J（回滚）会在若干代之后静默失效——而它正是产品的卖点之一。

另需复核约束本身：同 machine+digest 唯一在 digest 不随 generation 变时会让回滚目标行被去重，建议改为按 (machine_id, generation) 唯一 + digest 建索引。

**M4｜`Unknown` 操作没有权威裁决者，重启后可能永久悬挂。**
§9.6 只说 in-flight 操作置 `Unknown`，"直到 agent 重报最终结果或操作者重试"。若节点在变更完成后、上报前掉线，控制面没有任何机制终结这次操作，Machine 的 conditions 会停在不确定态，Deployment 门禁也拿不到结论。需要明确一条恢复原语：验证到节点在线后由控制面主动 `RequestInventory` 重新校准 conditions（协议里已有该消息，缺的是把它写成 Unknown 的裁决路径），并为 SSH 路径定义"重试前先清理远端临时目录 + 复用同一 operationId"的幂等语义——否则 scp 中途断线重试会撞上半截残留目录，而文档只写了正常路径的"上传 → plan → apply → 删除"。

**M5｜SSH-only 机器的 drift 是"不可知"，UI 必须区分"不可知"与"一致"。**
§2.3 已承认 SSH-only 节点 MVP 不做后台轮询，只在操作者触发或 Deployment 命中时收敛——这个取舍对单操作者 MVP 是合理的。但文档没有处理它的必然推论：这类机器的 `Drifted` 只能是 Unknown，而 FR-1.6 把六个 conditions 全列为"必填维护项"。若 UI 用 `Drifted=False` 表示"一致"，操作者会把"从未检查"读成"已确认无 drift"。需要为 SSH-only 定义独立的数据新鲜度语义（如 `Drifted=Unknown` + `lastProbedAt`），这与 §6.2 表格的现状直接冲突，得改表。

### 建议修（会造成运行期风险或返工）

**S1｜SSH-only 的 bundle 上传没有文件大小与配额模型。** ≤200 Skills 的目录若含大工件，一次 bundle 可能到数百 MB，经 scp 上传且占用全局 20 并发槽位中的一格数分钟。spec 与文档都没给 bundle 大小上界、分块或复用增量传输的设计。建议至少给出单 Skill 工件大小上限与超限时的显式失败码，避免"传了 10 分钟才失败"。

**S2｜20 并发上限与 45s 离线阈值之间存在隐蔽的相互作用。** 长 SSH 操作占满槽位会饿死 daemon 路径的变更请求，而心跳超时判定 `AgentConnected=False` 与操作队列是两条独立机制，文档（RD-6 带权信号量）没有把二者的相互影响写出来。建议按通道分别设配额，或给 daemon 路径保留最小并发数。

**S3｜enrollment 端点是最有吸引力的攻击面，但缓解措施停在"建议"。** 文档 §17 风险表（R6）把"失败限速（建议实现）"降级为可选项；但这是整个系统唯一的未认证写入口，且 RD-2 又推荐它与 gRPC 共用监听端口。建议升为强制项：限速、失败审计、按 machineId 的相关性检测，并明确 advertiseURL 在非 loopback 部署下必须为 TLS 终结（enrollment 明文 HTTP/2 会让 token 与 CSR 裸奔）。

**S4｜证书续期无抖动、无吊销。** 24h 量级证书 + 全部节点固定周期续期会把续期请求对齐到同一时刻；`agent_certificates` 表存了序列号却没有任何吊销或对账用途。建议续期窗加随机抖动，并把"哪里用到证书序列号"写清（至少用于手工吊销一个丢失节点）。

**S5｜CA 根密钥的丢失/轮换路径缺失。** §4.6 只说 CA 私钥留在控制面主机 0600。CA 私钥丢失 = 全机群需重新 bootstrap；被窃 = 全机群需重签。MVP 不做自动轮换可以接受，但文档应明确这是已接受的风险、恢复路径是"逐个经 SSH repair 重做 enrollment"，并说明是否需要离线备份根密钥——这属于必须在设计阶段定下来的运维契约。

**S6｜SQLite 单写与 WAL 的实际并发边界没建模。** §12.1 的容量估算只算了消息速率（100 机心跳约 6.7 msg/s，算术正确），漏了真正的串行点：全量 inventory 响应（每机每 5 分钟一次、负载可能数百 KB）与 SSE 读、控制循环写在单写锁上排队。WAL 允许并发读，但写仍是单写。建议补 busy timeout 与连接池写并发的明确取值，并把 SQLITE_BUSY 计入 §33 指标——它直接影响 NFR-2 的 1s plan 承诺。

### 可保留但需注明边界

- **plan <1s 的适用范围**：NFR-2 原文是"不含网络/包管理操作"，文档在 FR-9.5 忠实转引了。建议再补一句该指标隐含"daemon 模式 + 热缓存 + inventory 已完成"，否则 SSH-only 路径（含 scp 上传）会让读者误以为同一指标适用。
- **§8.3 的 digest 比较 vs §7.1 的逐字段比较**：见 M2，保留哪一个都行，但不能两个都当判据。
- **RD-2（enrollment 与 agent 共用端口）**：作为实现级决策可以保留，前提是 S3 的 TLS 与限速同时落地。

### 需要你确认的两处文档矛盾

1. **需求条数不一致**：§2.8 写"70 条子项，P0 = 69、P1 = 1"，§18 结论写"15 组功能需求 55 条子项"。我按文档表格逐组累加核对，两组数字对不上——请确认以哪份为准，这会影响 §13.3 验收映射的完整性核对。
2. **目录 ≤200 Skills 与 bundle 复用的关系**：若操作者长期只触发少数机器 reconcile，服务端工件缓存与节点规范缓存会双向增长，§10.3 的"引用计数清理（MVP 可仅手动）"是否可接受，需要你确认。

### 下一步建议

M1 与 M2 是同一处缺口的两个面，建议合并为一次设计修订：在 §6.3 快照结构里补 `projectionSchema` + `canonicalizationVersion`，在 §7.1 重画摘要职责边界，并同步修正 §4.2/§4.4/FR-8.3 的判据表述。M3～M5 各自可独立成一节，改动范围限于 §6.3、§9.6、§6.2。这四处改完后，验收 G（drift/reconcile）与 J（回滚）才具备可验证的判据。
