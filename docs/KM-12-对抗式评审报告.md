## 一、结论摘要

设计骨架（期望状态 → 快照 → 双通道派发 → 本地收敛 → 观测比对闭环）成立，首轮评审指出的摘要契约缺失（M1/M2）与回滚保留契约（M3）确认为真实缺口。本轮对抗式推演在此基础上发现 **4 个阻断项**，集中在并发与恢复语义：

| 编号 | 阻断项 | 一句话故障 |
|---|---|---|
| A1 | 节点侧变更串行化未定义 | `DesiredStateChanged` 触发的本地 apply 与 `ExecuteOperation` 派发的 apply 可在同一节点并发跑两条 13 阶段流水线 |
| A2 | Machine 级互斥未持久化 | 服务端重启后 Unknown 操作仍在节点执行，SSH 重试路径与 daemon 路径跨通道并发 |
| A3 | 条件/门禁未绑定当前 generation | 迟到操作按旧快照 verify 成功后可把 `Reconciled=True` 写在 gen13 时代；`CancelOperation` 全文无语义 |
| A5 | generation 回滚若走"还原备份"将覆盖未托管编辑 | 备份是整文件快照，还原会抹掉备份之后的用户手工修改，直接违反 I-6 |

另有高优先级 3 项（A4 门禁新鲜度、A6 SSH plan/apply TOCTOU、A8 enrollment 明文抢注+假节点毒化）、中优先级 4 项（A7、A9、A11、F6）、低优先级若干。首轮 M1–M5、S1–S6 复核结论：**5 项采纳（其中 3 项论据需修正）、1 项机制描述有误需降级**；首轮"projectionSchema 是唯一出路"与"同 machine+digest 唯一会导致回滚目标被去重"两个论断经推演**不成立**，详见第三节。

用户在 KM-3 追问的"需求条数不一致"已核实：**§2.8 的 70 条正确，§18 的 55 条是文档错误**（见第二节）。

## 三、首轮评审结论复核（不无条件照收）

### V-M1 摘要契约缺失 —— 核心结论采纳，"唯一方案"论断驳回

M1 正确识别了三种摘要（全量快照摘要 §4.8 / 期望侧受管投影摘要 FR-10.3、§4.4 / 观测侧受管投影摘要 §5.5、§7.1）被混用，且期望侧投影摘要 spec 未定义、arch 也未补。**这个缺口是真的**。

但 M1 的处方断言"期望侧投影**只能**由快照携带的 adapter schema 描述符（projectionSchema）+ 规范化规则算出来"——经推演存在一个同样自洽、且与 I-1（控制面零适配器知识）更彻底的替代方案：

> **比较全部在节点侧完成**：适配器本来就同时知道"归一化期望 → 原生受管字段"的映射（这就是 Apply 干的事）与"原生文件 → 受管投影"的提取（Inventory 干的事）。让节点在每次 inventory 时对**当前快照**同时计算 `desiredProjectionDigest` 与 `observedProjectionDigest` 并随 ObservedState 上报；服务端只存储、比较两个数、写条件。快照**不需要新增任何字段**（projectionSchema/canonicalizationVersion 都不需要进快照——规范化版本随 inventory 报文携带即可，用于诊断而非判据）；控制面从头到尾不做任何适配器语义计算，I-1 保持平凡成立；逐字段 diff 也由节点上报（展示用，顺带消解 M2 的判据二义）。

代价：服务端失去独立复核能力（节点说一致就是一致）、快照不自包含投影描述（跨工具审计变弱）。这正是需要 **ADR 权衡的选型**，而不是 M1 文本暗示的"补两个字段即可"的唯一路径。

**建议**：保留 M1 的"必须先定义比较契约"结论；把"快照携带 projectionSchema（服务端算投影）"与"节点双侧投影上报（节点算比较）"作为两个候选写 ADR，明确权威判据 = 期望投影摘要 vs 观测投影摘要、全量快照摘要仅用于内容寻址身份。M2 的"摘要做判据、diff 做展示"在两个候选下都成立，采纳。

**验收**（选型后）：同一 fixture 下，两方案各自的 drift 判定、diff 展示、断线重连后重算路径均有单测。

### V-M2 drift 判据内部矛盾 —— 采纳

§4.2/§4.4（摘要式）与 §7.1（逐字段式）、FR-8.3（摘要式）并存，判据二义真实。修法依赖 V-M1 选型（两个候选里摘要都是权威判据）。采纳，无修正。

### V-M3 快照保留契约缺失 —— 主结论采纳，唯一性约束论据错误

主结论采纳：§10.3 数据保留覆盖了备份/observed_states/Skill 工件/events，唯独没有 desired_snapshots；"快照永不回收"应显式写明（100 机 × 数千代的快照 JSON 在 MVP 规模下总量很小，成本可忽略，永久保留是正确缺省）。

**但 M3 的复核论据"同 machine+digest 唯一在 digest 不随 generation 变时会让回滚目标行被去重"不成立**：按 arch 自己的 FR-7.2/§4.8 语义，generation 仅在摘要变化时递增、摘要相同不产生新行——因此同一机器上**不同 generation 必然对应不同 digest**，(machine_id, digest) 唯一与 (machine_id, generation) 唯一在既有语义下是等价约束，不存在"回滚目标行被去重"的情形。M3 据此提出的改法（改按 generation 唯一）是无操作。

真正的问题在别处——**A→B→A 回退序列**（见新发现 F6）：profile 从内容 A（gen12）改到 B（gen13）再改回 A 时，摘要相对上一代变了 → generation 须递增到 14，但 (machine, digestA) 行已存在且其 generation 列 = 12，内容寻址行与代计数语义冲突，Deployment 的 targetGeneration=14 无行可指。这是 M3 没打中的真问题。

### V-M4 Unknown 操作无裁决者 —— 方向采纳，"重新 inventory"的能力边界必须写清

M4 建议用 `RequestInventory` 重新校准 conditions 来终结 Unknown。推演结论：**inventory 能修复的是 conditions，不是 Operation 记录，更不是 Deployment 门禁**。三者必须分开定义：

1. **conditions**（Drifted/Reconciled）：inventory 可修复——观测与当前期望比对即可重写，采纳 M4；
2. **Operation 记录**：FR-10.3 门禁第一条件是"操作成功"。operation 置 Unknown 后，任何 inventory 都无法把"历史操作是否干净完成"变成事实（重新 inventory 只能证明**现在**匹配，不能证明**当时**没有触发过恢复路径、没有半途失败）。若允许"inventory 匹配 ⇒ 操作记成功"，等于虚造审计事实，违反 §35.2 "unless a later agent report proves their final result" 的本意——spec 要的是**节点报告**，不是服务端推断。落地机制：**agentd 结果 outbox**（本地持久化最近 N 条 OperationResult，重连后重发，服务端按 operationId 幂等去重）才是"后续 agent 报告"的具体化，建议写入 §5.2/§8.2；
3. **deployment_targets**：需要显式策略——Unknown 的目标机是"阻塞批次等待重报"还是"按失败暂停"。§4.4 目前只说"等待 agent 重报或操作者重试"，没说批次推进怎么算。建议 MVP 取"阻塞 + 可操作者显式跳过"，宁停不错。

M4 的 SSH 路径补充（重试复用同一 operationId + 先清理远端残留）采纳，并入 A10。

### V-M5 SSH-only 的 drift 不可知 —— 采纳，附 spec 兼容性论证

采纳：SSH-only 机器两次操作之间 `Drifted=False` 会被读成"已确认一致"，必须区分"未知/过期"。补充论证其 spec 兼容性：K8s 条件模型 status 本就允许 `Unknown`；spec §8.2 示例只用了 "True"/"False" 但未禁止第三态，spec §35.2 已有 `Unknown` 先例。最小改动 = §6.2 表为 `Drifted` 增加 Unknown 取值 + UI 以 `lastInventoryAt` 新鲜度呈现，与 spec §22 "存显式控制器决策"不冲突。

### V-S1 bundle 大小/配额模型缺失 —— 采纳【实现建议】

spec NFR-1 无工件大小上限，SSH bundle 经 scp 占用全局并发槽位数分钟的风险真实。建议：单 Skill 工件大小上限 + 超限显式失败码 + bundle 总量预算，写进 §7.4。

### V-S2 20 并发与 45s 离线的"隐蔽相互作用" —— 机制描述有误，降级为低

复核结论：心跳不经变更信号量（RD-6 只约束变更操作），长 SSH 操作占满槽位**不会**让 daemon 路径的心跳被饿死，`AgentConnected` 判定与操作队列本就是两条独立机制，不存在 S2 所述的相互作用。真实的、弱得多的问题是：长 SSH 操作占满 20 槽位时，**新变更请求**排队延迟不可见。降级为低，修法保留（分通道配额或至少暴露队列深度指标）。首轮该条按"运行期风险"定级偏高。

### V-S3 enrollment 缓解停在"建议" —— 采纳并强化

S3 方向正确。本轮给出比"token 与 CSR 裸奔"更具体的攻击链（A8：明文 token 抢注 → 假节点顶替 → 毒化 canary 门禁），并把"限速/审计/相关性检测升为强制"与"advertiseURL 必须 TLS"落成 RD-2 的修订要求。采纳，详见 A8。

### V-S4 证书续期无抖动、序列号无消费方 —— 采纳【实现建议 + 一处超范围界定】

采纳：续期窗口加随机抖动（低成本）；`agent_certificates` 序列号至少明确一个用途（MVP：机器删除时记录"该序列号至到期前仍有效"的审计事实；手工吊销属【超范围增强】，完整 CRL/OCSP 明确不做）。补充关联缺口：机器删除后证书至自然过期前仍然有效（无吊销路径）——单操作者威胁模型下可接受，但 §10.1 应写明这一已接受风险，与 S5 的 CA 风险声明并列。

### V-S5 CA 根密钥丢失/轮换路径缺失 —— 采纳

采纳：设计阶段就把"CA 私钥丢失 = 全机群重新 bootstrap、被窃 = 全机群重签"写成已接受风险与恢复契约，并明确 MVP 不做根密钥离线备份的取舍。

### V-S6 SQLite 单写边界未建模 —— 结论保留，论证纠正

busy timeout、写并发取值、SQLITE_BUSY 计入指标——保留，是好卫生。**但 S6 的因果链有一处错误**：它声称 SQLITE_BUSY "直接影响 NFR-2 的 1s plan 承诺"。NFR-2 的 plan 计算发生在**节点侧**（reconciler 阶段 3 在 agentd 本地执行，arch §5.3、§3.4 流 1），服务端 SQLite 写竞争不进入该路径；SQLite 争用影响的是控制循环写、条件更新与 UI 延迟，不影响 NFR-2。§12.1 的容量估算数字本身（6.7 msg/s、0.33 台/s）复核无误。

## 四、对抗式新发现

### A1【文档缺口｜阻断】节点侧变更执行串行化未定义，双通道互斥只有控制面一半

**位置**：arch §4.3（"同一机器同时只允许一个变更操作（由 Machine 级互斥保证）"）；arch §3.4 流 1（"本地 reconciler plan（可自动 plan，apply 按策略/操作者触发）"）；arch §5.2（daemon 操作执行）；spec §11.4。

**故障时序**：
1. 操作者保存 profile → gen13 生成，服务端向在线节点推送 `DesiredStateChanged{13}`；
2. agentd 按"策略"（arch 未定义该策略）开始本地自动 apply——这条路径不产生服务端 Operation 记录，不在控制面互斥的覆盖范围内；
3. 同一时刻操作者点击 Reconcile → 服务端持 Machine 级互斥（自认为独占）→ 派发 `ExecuteOperation`；
4. 节点上两条 13 阶段流水线并发：备份目录交错、阶段 6/8 的原子写互相覆盖、任一失败触发的恢复动作回滚的可能是**对方**刚写入的内容。

**破坏的不变量**：I-5（先备份、失败恢复——恢复基线在并发下失真）；FR-9.3（幂等承诺隐含串行执行前提）；FR-9.2（失败语义无法归属）。

**建议最小修改**：(a) 规定 agentd 以**单 worker 串行队列**执行一切变更，`ExecuteOperation` 与本地自动 apply 一律入队；(b) 本地自动 apply 也必须持有服务端可见的 operationId（即"自动 apply"= 服务端下发的普通操作，或至少上报为 Operation）；(c) 控制面 Machine 级互斥明确覆盖 daemon 与 SSH 两条派发路径（在派发点获取、操作终态释放）。

**验收场景**：gRPC 集成测试——近同时注入 `DesiredStateChanged{13}` 与 `ExecuteOperation{gen13}`，断言节点串行执行、第二个操作观察到第一个的结果、恰好一条备份链、终态 desired==observed、conditions 无抖动。

### A2【文档缺口｜阻断】Machine 级互斥未持久化：重启后 Unknown 操作与 SSH 重试跨通道并发

**位置**：arch §4.3（互斥实现未指明，按 §3.5 单进程语境默认为内存信号量）；arch §9.6（in-flight 置 Unknown）；arch §4.4（Deployment 重启恢复）；spec §35.2。

**故障时序**：
1. `ExecuteOperation{op1, gen12}` 经 daemon 通道派发，agentd 开始执行慢安装（数分钟）；
2. 服务端进程崩溃重启 → op1 按 §9.6 置 Unknown，**内存互斥随进程消失**；
3. 操作者看到 `AgentConnected=False`（心跳尚未恢复）但 SSH 可达，触发 SSH oneshot reconcile → 服务端互斥已丢，视为空闲，构建 bundle{op2} 上传执行；
4. 同一台机器上：daemon 进程内的 op1 流水线与新起的 oneshot 进程 op2 并发——这正是 §4.3 想避免的"备份/恢复交错"，且跨了 daemon/SSH 两条通道。

**破坏的不变量**：I-5、I-7、FR-9.2/9.3；同时使 A1 的节点侧串行化成为唯一防线（两道防线缺一不可）。

**建议最小修改**：(a) 互斥以持久层表达——operations 表加"每台机器至多一个非终态（非 Succeeded/Failed/Superseded）操作"的部分唯一约束，重启后互斥自然恢复；(b) 处于 Unknown 的机器，新操作默认拒绝（或强制先走显式取消/跳过流程），UI 给出"该机有未决操作"的原因。

**验收场景**：故障注入测试——派发 op1 后重启服务端进程，立即经 SSH 触发 reconcile，断言 op2 被拒绝/排队，节点上任意时刻只有一条流水线在跑；op1 的 outbox 重报到达后正常终态化。

### A3【文档缺口｜阻断】条件与门禁未绑定"当前期望 generation"，迟到操作可写错状态；CancelOperation/Superseded 语义缺失

**位置**：arch §4.3（"操作完成后核对 apply 后 inventory 的摘要以决定 Reconciled/Drifted"——未指明对哪个 desired 求值）；arch §9.2（"摘要 == 期望 → Drifted=False, Reconciled=True"同此歧义）；arch §6.2 置位表；arch §8.2（`CancelOperation{operationId}` 出现在消息表但全文无任何语义定义）；arch §21.4/§7.3（回滚 Deployment 与并发 profile 编辑的交互未定义）；spec §21.3、§22。

**故障时序（迟到操作覆盖新代语义）**：
1. `ExecuteOperation{op1, gen12}` 派发，慢安装进行中；
2. 操作者编辑 profile → gen13 生成并推送（profile 保存不占用 Machine 变更互斥，与 op1 并行是常态）；
3. op1 完成：节点侧阶段 11–12 针对随操作下发的 **gen12** 快照 verify 通过，上报成功；
4. 若服务端按"操作目标代的快照"判定 → 写 `Reconciled=True`——而机器当前期望已是 gen13，实际状态落后一代，UI 显示"已收敛"是错的。

**反向时序（条件抖动）**：§4.2 置位表允许任意 `ObservedState` 消息改写 Drifted/Reconciled；操作刚完成、apply 后 inventory 尚在途时，一个排队的**操作前**周期 inventory 迟到到达，摘要基于旧状态 → 条件被错误改写后再被纠正，期间 Deployment 门禁若恰好采样即误判（与 A4 叠加）。

**破坏的不变量**：I-7（"desired==observed"中 desired 指代不明）；FR-8.3/FR-10.3；FR-1.6（条件须为控制器显式决策——决策输入必须唯一确定）。

**建议最小修改**：三条规则 + 一条协议语义：
- (a) `Drifted`/`Reconciled` **永远对机器当前 desired 快照**求值，任何操作结果不直接写这两个条件，只触发重新求值；
- (b) 操作完成时若其 desiredGeneration < 当前 generation → 终态记 `Succeeded(Superseded)`，不触发 Reconciled；是否有后续操作由 gen13 的派发逻辑决定；
- (c) Deployment 控制器推进前检查：targetGeneration < 机器当前 generation → 该目标置 `Superseded`，Deployment 终止（而不是把机器"拉回旧代"造成回退震荡——回退只应通过显式 rollback 发生）；
- (d) 定义 `CancelOperation`：仅在 13 阶段的阶段边界生效；处于可变阶段 5–10 时取消 = 走标准备份恢复路径后终态 `Failed(Cancelled)`；重复取消幂等；对 Unknown 操作取消仅在节点可联系时有效。

**验收场景**：时序测试——reconcile@gen12 进行中升级 gen13；断言 op1 终态 Superseded、`Reconciled` 不为 True、`Drifted=True`（对 gen13）；随后 reconcile@gen13 正常收敛。取消用例：apply 阶段注入取消，断言恢复执行且终态可审计。

### A4【文档缺口｜高】Deployment 门禁证据无新鲜度/因果绑定，陈旧状态可放行金丝雀

**位置**：arch §4.4（"门禁评估依赖 apply 后 inventory 上报"——未定义"哪份 inventory 才算数"）；arch §4.2（任意 ObservedState 写 conditions，status 中 observedDigest 是缓存值）；FR-10.3；spec §21.3。

**攻击/故障时序**：
1. 机器 A 曾与 gen12 一致，`status.observedDigest == desiredDigest` 缓存成立，健康检查记录也在；
2. 用户本地手改受管字段 → 节点 drift 上报因断线**丢失**；
3. 操作者基于 UI 现状（显示一致）对 A 所在批次 resume/重建 gen12 Deployment；
4. 门禁读取缓存 status：摘要相等 + 历史健康记录通过 → 金丝雀"健康"，批次推进——而 A 实际处于 drift，且从未在本次操作后上报过任何证据。

**破坏的不变量**：FR-10.3 四条件的证据语义；I-7。

**建议最小修改**：门禁证据三元组必须**因果绑定且晚于本次操作**（以服务端接收序为准，避免节点时钟依赖）：(1) 操作成功且 desiredGeneration == target；(2) 一份 `reportedAt > op.finishedAt` 的 inventory，其投影摘要 == 目标快照投影摘要；(3) 同样晚于操作完成的健康检查通过。禁止从缓存 status 直接判门禁。

**验收场景**：集成测试——构造"status 缓存匹配 + 最新真实上报 drift"的机器，断言 Deployment 对其不放行、目标呈现"证据过期"原因；正常路径（操作后 inventory 及时到达）不受影响。

### A5【文档缺口｜阻断】generation 回滚若实现为"还原备份"，将覆盖回滚窗口内的未托管编辑

**位置**：arch §7.2（"事后回滚（API/UI）| 配置/文件类：恢复上一成功操作的备份"）；arch §6.3（"回滚 = 将机器重指向前一快照 generation"）——两条回滚机制并存、无择一规则；spec §3.5、§16、§34.D、护栏 #3、§20.3。

**故障时序**：
1. gen12 应用：备份 B12 = 当时整文件内容（含用户未托管键 `customSetting=foo`）；
2. 11:00 用户手工加入未托管键 `customSetting=bar`；
3. 12:00 gen13 应用（备份 B13 含 `bar`）；
4. 14:00 操作者执行"回滚到 gen12"（spec §21.4 / arch §6.3 的语义）。若按 §7.2 走备份还原、取到 B12 → 整文件回写 → **`customSetting=bar` 静默丢失**。

**破坏的不变量**：I-6（未托管字段永不因 Fleet 操作而丢失——回滚同样是 Fleet 对用户文件的变更，应受同一不变量约束；spec §34.D/护栏 #3 的字面只覆盖 apply，但 I-6 的措辞与 spec §3.5 的意图是全覆盖的）。

**建议最小修改**：(a) 明确**面向 generation 的回滚统一实现为对目标快照的重放 reconcile**——走适配器合并写（天然保留未托管字段）、经阶段 11–12 验证，语义与 §6.3 一致；(b) 备份还原仅保留给**操作内失败恢复**（§14.2，此时整文件还原的基线是"本操作开始前的最后已知完好状态"），并在文档标注已接受限制：操作窗口内的未托管编辑可能丢失；(c) 删除 §7.2 中"事后回滚=恢复备份"一行或改为指向重放。

**验收场景**：适配器 fixture 测试——gen12 → 手工加未托管键 → gen13 → 回滚到 gen12；断言未托管键保留、受管字段等于 gen12 内容、apply 后验证通过、Operation 记录为 Rollback 成功。反例（操作内恢复）：注入阶段 6 失败，断言整文件还原后与操作前逐字节一致。

### A6【文档缺口｜高】SSH-only plan/apply 两阶段 TOCTOU：确认的计划与实际执行可以不一致

**位置**：arch §7.4（执行序：`oneshot plan` → 操作者确认 → `oneshot apply`）；arch §9.3（"plan 输出在人发起的路径上可回显给操作者确认"）；spec §13.4。

**故障时序**：
1. `oneshot plan --bundle` 输出计划 P（基于时刻 T 的观测）；
2. 操作者审阅期间（或 Deployment 排队等待并发槽位期间），本地受管文件被用户或其它进程修改；
3. `oneshot apply --bundle` 执行——arch §5.1 将 oneshot apply 描述为"备份→应用→验证"（未含重新 plan），若它直接执行 P：把基于旧观测的计划套在已变化的现状上；若它内部重新 plan：操作者确认的 P 与实际执行的计划不同，"确认"失去意义。两种语义 arch 都未规定。

**破坏的不变量**：FR-9.2（变更行为可预期）；I-5（恢复基线错位时恢复结果不可预期）。

**建议最小修改**：规定 `oneshot apply` 必须**重算 plan**，并把重算基线（阶段 2 观测摘要）与 plan 阶段记录在 bundle/输出中的基线比对：不一致 → 拒绝执行并要求重新 plan（新增错误码 `ReplanRequired`，归入 §30.3 Reconcile 错误组——顺带修复下文小项 a 的错误码缺口）。

**验收场景**：SSH 集成测试——plan 与 apply 之间修改受管文件，断言 apply 拒绝、零变更、错误码 `ReplanRequired`；基线未变时正常执行且与展示计划一致。

### A7【文档缺口｜中】Skill 名称/digest 字段与解包路径安全未约束

**位置**：arch §7.4（bundle 结构与"apply 校验 digest"）；arch §4.7、§5.5、§10.2（节点缓存路径 `skills/<skill-name>/<digest>/`）；spec §17.3、§29.11；O2 只讨论了 symlink 是否入哈希。

**攻击/故障时序**：
1. manifest.json 中某 Skill 条目的 name 字段（源自 profile，经 bundle 下发）或 digest 字段若为 `../../.ssh/` 形态（服务端缺陷、或被篡改后未校验），节点解包/物化时路径拼接逃逸出缓存根目录，配合 0700 home 权限写入任意位置；
2. symlink 模式下，适配器把 Agent Skill 目录链接向逃逸后的目标，Agent 运行时读取该路径 → 代码/指令注入面；
3. Skill **内容**来自外部 Git 仓库（唯一外部数据依赖，§3.2）：仓库内可包含符号链接条目，解析/缓存/解包对内容内 symlink 的策略（O2）只谈哈希、没谈**逃逸**——内容内 symlink 指向根外即可在物化时把代理写穿。

**破坏的不变量**：§29.11 的意图（节点只信任 digest 验证过的工件）；节点文件完整性。

**建议最小修改**：(a) digest 字段强格式校验 `^sha256:[0-9a-f]{64}$`；(b) bundle 条目名禁止绝对路径与 `..` 段，解包在固定根内做边界检查；(c) skill-name 白名单 `^[A-Za-z0-9._-]+$`；(d) MVP 对 Skill 内容内的符号链接一律拒绝解析（报明确错误码），或严格限定在工件根内。

**验收场景**：恶意 fixture bundle（含 `..` 条目、坏 digest 格式、内容内 symlink 逃逸三类样本）——断言节点全部拒绝、错误码明确、无任何根外写入（临时 HOME 下验证）。

### A8【spec 冲突 + 文档缺口｜高】enrollment 通道明文化（RD-2 推荐项）+ 重复连接策略未定义 → token 抢注与假节点毒化门禁

**位置**：arch RD-2（"推荐 enrollment 复用同一 gRPC 监听端口的 HTTP/2 **明文**路径"）；arch §4.6、§7.5、§8.2；spec §11（"protobuf + bidirectional gRPC **over TLS**"）、§29.5（mTLS 强制）。

**攻击时序**：
1. bootstrap 经 SSH 下发 agentd.yaml（**已含 CA 证书**，§7.5）→ agentd 发起 enroll。按 RD-2 推荐项走同端口明文 HTTP/2：`{machineId, token, CSR}` 全程明文；
2. 同网段窃听者截获三元组，与真实 agentd 竞速——先到者赢得一次性 token，获得该 machineId 的**合法客户端证书**；真实节点 enroll 失败（token 已作废）；
3. 攻击者持合法证书建立 Connect 流。服务端对同一 machineId 的**重复连接策略全文未定义**（挤掉旧流？拒绝新流？并存？）——若实现为"新连接挤掉旧流"，攻击者顶掉真实节点（或真实节点尚未连上，攻击者就是唯一"该机"）；
4. 攻击者以该机身份上报伪造 ObservedState / 伪造 `OperationResult{Succeeded}` → A4 的门禁若再加新鲜度约束之前的版本会放行；即使加了新鲜度，伪造的"操作后 inventory"同样满足因果绑定 → **金丝雀判健康，坏配置推向全机群**；
5. 审计链（Operation/conditions）被投毒，事后无差异可查（fake 结果与真成功在记录上不可区分）。

**破坏的不变量**：spec §11/§29.5（传输 TLS 语义被 RD-2 例外侵蚀——arch §1.1 自订"冲突以 spec 为准"，RD-2 的推荐方向实际与 spec 冲突却未标注）；I-3 的配套审计可信性；FR-10.3。

**建议最小修改**：(a) RD-2 修订为：**enroll 必须经 TLS**——节点 bootstrap 时已获 CA 证书，做服务器端证书校验即可（无需 mTLS，token 仍是身份证明），消除明文 token；(b) token 熵明确 ≥128-bit 随机；(c) 定义重复连接策略：同 machineId 并发第二连接默认**拒绝并告警**（若产品语义需要顶替，须先验证新连接持有同一私钥——Connect 握手挑战）；(d) 失败限速/审计从"建议"升为强制（采纳 S3）。【超范围增强，仅记录】备选方案"enroll 直接复用 SSH 通道回传 CSR"可彻底消除网络明文面，但改变协议边界，不建议 MVP 实施。

**验收场景**：集成测试——(1) 截获 enroll 报文重放 → 失败（token 一次性）；(2) 明文监听断言无 token 可见（TLS 生效）；(3) 双连接并发 → 第二连接被拒且产生告警事件；(4) 攻击者持旧证书连接 → 被服务端挑战（证明私钥）拒绝。

### A9【文档缺口｜中】ExecuteOperation 以"摘要引用"携带期望状态时，节点无获取快照的协议路径

**位置**：arch §8.2（`ExecuteOperation{operationId, snapshot 或摘要引用}`）；arch §8.2 服务列表（`FetchArtifact` 仅覆盖 Skill 工件）。

**故障时序**：节点重启且本地未持久化最近快照 → 服务端推送 `ExecuteOperation{digest 引用}`（为省流量选了引用形态）→ 节点无任何消息/RPC 可取回快照（FetchArtifact 语义限于 Skill 工件）→ 操作必然失败，且 §30 错误模型中没有对应 reason。

**破坏的不变量**：FR-13.1/FR-13.4 的协议完备性（服务端"不下发节点看不懂的状态"的承诺无法兑现）。

**建议最小修改**：MVP 规定 `ExecuteOperation` **一律携带完整快照**（归一化 JSON 在目标规模下为 KB 量级，引用优化无必要），并在 §8.2 注明"摘要引用形态留待 Post-MVP 配套 GetSnapshot RPC"；或立即为 FetchArtifact 增加快照对象语义。

**验收场景**：协议测试——节点冷启动（无本地快照缓存）后收到完整快照型 ExecuteOperation，断言正常执行；若保留引用形态，断言节点显式报错而非静默失败。

### A10【文档缺口｜低】崩溃遗留远端 bundle 临时目录泄漏

### A11【文档缺口｜中】spec §4.1 明示 in-scope 的 "automatic reconcile" 无任何 FR 承载、无策略定义

**位置**：spec §4.1（"Manual and automatic reconcile"）；arch §2.4 FR-9（仅 FR-9.4 手动 + Deployment 两入口）；arch §3.4 流 1（"apply 按策略/操作者触发"——策略未定义）。

**故障时序（设计后果而非运行事故）**：实现团队读到 spec in-scope 列表认为必须做自动收敛，读到 FR 表认为不必做——两份"实现依据"（arch §1.1 明言两者共同构成依据）给出相反信号；若做了自动 apply 又没有触发策略定义，直接放大 A1 的并发窗口。这是需求拆解的**完整性缺口**（spec 明确要求未被 FR 表承载），也回应 §2.8 "全部可在 FR 表中找到承载条目"的例外。

**建议最小修改**：二选一并写明——(a) MVP 明确收缩为"仅手动 + Deployment 驱动"，在 FR-9 与 §2.6 标注"automatic reconcile 为 spec in-scope 项的显式延期，需 owner 确认"（这属于对 spec 的偏离，按 arch §1.1 规则应回写 spec 或经 owner 批准）；(b) 或补 FR-9.7 定义自动收敛策略（建议：仅 drift 自动 re-plan/上报、apply 恒需触发——与 §10.4 的 drift 上报语义衔接）。

### F6【文档缺口｜中】快照内容寻址与 generation 语义在 A→B→A 回退时冲突

**位置**：arch §10.1（desired_snapshots "同 machine+digest 唯一"）；arch §4.8（"摘要相同则不递增 generation、不产生新行"）；arch §6.3。

**故障时序**：
1. 机器快照内容 A（gen12）→ profile 改动 → 内容 B（gen13）→ profile 改回 → 内容 A；
2. 相对上一代（B）摘要已变化 → generation 须递增至 14；但 (machine, digestA) 行**已存在**（其 generation 列 = 12）——按"摘要相同不产生新行"不再新建；
3. 结果：machine.generation = 14，指向的行却声称 generation = 12；`Deployment.targetGeneration = 14` 无行可指；回滚到"gen13"（内容 B 的行）再回滚到"gen12"的语义全部含混。

**破坏的不变量**：FR-7.2 的语义自洽（generation 作为代计数与内容寻址被混在一张表）；FR-10.4（回滚目标"既往 recorded generation"的可达性）。

**建议最小修改**：拆开两个概念——`snapshot_contents(machine_id, digest UNIQUE, json)` 存内容；`generation_history(machine_id, generation UNIQUE → digest 外键, created_at)` 只追加存代序列；machine 与 Deployment 一律引用 (machine_id, generation)。(machine_id, digest) 唯一约束保留在内容表上，行为与 FR-7.2 完全一致，且 A→B→A 自然产生 gen14 → 内容 A 的正确映射。（这也是对 V-M3 的最终修正：M3 提的"改按 generation 唯一"方向歪打正着，但论据须替换为 A→B→A 冲突。）

**验收场景**：单测——构造 A→B→A 序列，断言 generation=14、内容行仅 2 条、回滚到 gen13 与 gen12 均可达且 Deployment 引用有效。

## 七、修订优先级建议

1. **一次设计修订解决 A1+A2+A3**（同一主题：变更的串行与代语义）——节点单 worker 队列、持久化互斥、"条件永远对当前代求值 + Superseded 规则 + CancelOperation 语义"。这三条不定，FR-9/FR-10 的所有验收在边界场景不可复现。
2. **A5 独立成节**：回滚语义统一为"重放目标快照"，备份还原收缩到操作内恢复——这是 I-6 的直接修补，改动仅 §7.2/§6.3 两处表述。
3. **A8 = RD-2 重写**：enroll 走 TLS + token 熵 + 重复连接策略 + 限速强制。
4. **A4/A6 随门禁与 SSH 路径修订**：证据新鲜度绑定 + apply 重算 plan + `ReplanRequired` 错误码。
5. **ADR 一份**：drift 比较位置选型（V-M1 两候选），顺带落 M1/M2 的契约文本。
6. **owner 决策两项**：A11（automatic reconcile 进不进 MVP）、M5 的 SSH-only Unknown 语义 UI 呈现。
7. 其余中低项可随实现推进消化；F6 建议在首版 schema 迁移前定稿（表结构返工成本最高）。
