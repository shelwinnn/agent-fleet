## 0. 本文能做什么、不能做什么

**能做什么**

- 告诉你在什么时候、由谁、备份哪些材料，才能让"CA 丢失"变成**可恢复事件**而不是"全机群重建"。
- 给出默认采用**离线一致性方案**的人工备份与恢复步骤、校验清单和停止条件。
- 区分并分别处理：**CA 丢失（有可用备份）**、**CA 丢失且无可用备份**、**CA 泄露**。
- 给出演练（DR-1～DR-8）的步骤、成功判据与记录模板。

**不能做什么（重要边界）**

- **本文不是产品功能**。MVP **不提供**内置的 CA 备份导出 API、CLI 子命令或 UI 入口（用户已决）。因此本手册中出现的命令**全部是通用系统工具（`tar` / `openssl` / `sqlite3` / `sha256sum` / `gpg` 等）的示例**，不是产品接口。
- **本文不声称已演练通过**。所有演练项当前状态为"计划已定义、未执行"。任何"CA 已可恢复"的结论，必须引用一份**已填写**的演练记录（附录 A）。
- **本文不保证在线热备可用**。默认方案是**停机离线备份**；在线备份需要你自证其一致性，本手册不为其背书。
- 本文不改变 spec，也不新增产品需求。

## 1. 角色、责任与前置条件

### 1.1 角色与责任

| 角色 | 责任 |
|---|---|
| 单操作者（或经授权的运维执行者） | 执行备份、保管介质与口令、执行恢复、执行并记录演练。**责任不可转移给产品**——产品不发起备份，也不检测备份是否已做 |
| 产品（agent-fleet-server） | 只负责在控制面主机上维护 `pki/`、`fleet.db`、`config.yaml`、`artifacts/`。**不导出、不提醒、不校验备份是否存在** |

### 1.2 前置条件（全部满足才可开始）

1. 你是控制面主机的管理员，能停止/启动 `agent-fleet-server` 进程；
2. 你能在操作者控制的**加密介质或加密存储**上写入（见 §5）；
3. 你能安排一个**维护窗口**，期间不会有人触发机群变更（Deployment、reconcile、机器添加/删除）；
4. 至少一台**已知可信节点**当前处于连接状态或可被 SSH 触达（用于恢复后连接验证）；
5. 主机上有通用工具：`tar`、`sha256sum`（macOS 为 `shasum -a 256`）、`openssl`；涉及数据库一致性检查时需要 `sqlite3`；
6. 你已确认本机的实际产品路径与 §3 的占位符对应（架构 §10.2 是布局约定，不是运行时探测结果）。

### 1.3 占位符约定

| 占位符 | 含义 |
|---|---|
| `<DATA_DIR>` | 控制面数据目录，架构默认 `~/.local/share/agent-fleet` |
| `<CONFIG_DIR>` | 控制面配置目录，架构默认 `~/.config/agent-fleet` |
| `<MEDIA>` | 操作者控制的加密介质挂载点（如已解锁的加密卷） |
| `<STAGE>` | 本机临时暂存目录（**必须位于加密卷内或在本机磁盘上且用完即删**） |
| `<STAMP>` | 时间戳，建议 `YYYYMMDD-HHMM`（UTC） |
| `<HOST>` | 控制面主机名 |

**注意**：`<STAGE>` 会短暂承载私钥明文。若本机磁盘未加密，应把 `<STAGE>` 直接放在已挂载的加密介质内，或全程以管道方式流式复制，避免明文落盘。

## 2. 备份内容及边界（对应架构 §4.6 第 3 条）

### 2.1 清单

| # | 类别 | 架构默认路径（占位符） | 作用 | 必要性 |
|---|---|---|---|---|
| 1 | CA 根私钥 | `<DATA_DIR>/pki/ca.key`（权限 0600） | 继续为本机群签发/校验客户端证书的能力 | **必须** |
| 2 | CA 根证书 | `<DATA_DIR>/pki/ca.crt` | 校验 `ca.key` 配对、作为客户端校验的信任锚 | **必须** |
| 3 | 服务端私钥 | `<DATA_DIR>/pki/server.key`（0600） | `advertiseURL` 的 TLS 终结点身份 | **必须**（否则需重签服务端证书，客户端信任链条变动） |
| 4 | 服务端证书 | `<DATA_DIR>/pki/server.crt` | 同上 | **必须** |
| 5 | 控制面配置 | `<CONFIG_DIR>/config.yaml` | `advertiseURL`、监听、admin token 等配置 | **必须** |
| 6 | 身份与控制面元数据 | `<DATA_DIR>/fleet.db` | `machines`（machineId ↔ 机器身份）、`agent_certificates`（已签发证书序列号/有效期/删除事实）、`desired_snapshots`、`operations` | **必须**（要恢复"能起且身份对应"） |
| 7 | SQLite 旁路文件 | `<DATA_DIR>/fleet.db-wal`、`fleet.db-shm`（若存在） | WAL 模式下的一致性 | 视实际模式：停机并 checkpoint 后通常可只取主库（见 §4.3） |
| 8 | 技能工件 | `<DATA_DIR>/artifacts/skills/` | 恢复后可直接 reconcile | 条件必须：**若恢复目标仅是"控制面能起"**，可暂不备份；**若目标是"恢复后立即能对节点 reconcile"**，必须一并备份 |
| 9 | agentd 工件 | `<DATA_DIR>/artifacts/agentd/` | repair/bootstrap 时下发二进制 | 条件必须（同上） |
| 10 | Git 缓存 | `<DATA_DIR>/git-cache/` | Skill 解析可复现 | 可选（可重新拉取，但需网络与源可达） |

### 2.2 关键边界：**只备份 CA ≠ 控制面完整恢复**

- 只恢复 `ca.key`/`ca.crt`：只能保证"信任根"延续，但控制面**没有** machineId ↔ 机器的对应关系、没有期望代、没有操作审计，无法在既有身份下继续工作。
- 只恢复 `fleet.db` 而不恢复 CA：控制面起来后**无法通过既有节点的 mTLS 校验**（客户端证书由旧 CA 签发，而库里的信任锚已变），节点连接会失败。
- 因此第 1～6 项必须**成套、同源、时间一致**。这不是可选项，而是恢复前检查的显式判据（§6.1）。

### 2.3 不在备份范围

- **API key 值、SSH 私钥内容**：产品本就不持久化（架构 §11.1/11.2），无需也无法从控制面备份。若你另有存放，请用你自己的秘密管理方式，不要混入本手册的备份包。
- **节点侧 `client.key`**：属于各节点本地。CA 恢复后节点私钥不需要更换；**丢失的是 CA（分支二）时**才需要重新 enroll（§6.3）。

## 3. 备份执行时机

产品**不会**提醒你。由操作者按下表自行触发：

| 触发时机 | 为什么 | 优先级 |
|---|---|---|
| CA 首次生成后**立即** | 此刻尚无任何可用备份，处于"零可用备份"状态 | **最高** |
| CA 材料变更后（重新生成 CA、更换 `server.crt/key`） | 旧备份与实际信任锚不再一致 | **最高** |
| 机群结构发生较大变化后（批量增删机器） | `fleet.db` 身份元数据变化大，早先备份价值下降 | 中 |
| 周期复核（**建议不超过 90 天**） | 防止备份静默腐坏，并触发可恢复性抽查 | 中 |
| 证书**续期**发生时 | **不需要**重做 CA 备份：续期不改 CA 根密钥；仅当续期同时更换服务端证书时才按上表第 2 行处理 | — |

## 4. 人工备份流程（默认：离线一致性方案）

### 4.0 总览

| 步骤 | 动作 | 成功判据 |
|---|---|---|
| 1 | 准备维护窗口与加密介质 | 介质已解锁可写；维护窗口内无他人操作 |
| 2 | 停止变更、停止控制面 | `agent-fleet-server` 已停止；无进行中的 Deployment/reconcile |
| 3 | 确认无并发写 | 无进程持有 `fleet.db`/`pki`；WAL 已安全处理 |
| 4 | 复制材料到暂存区 | 1～10 项按需复制完成，权限保持 |
| 5 | 校验 | 摘要一致、CA 配对、证书可校验、权限正确 |
| 6 | 生成备份清单与元数据 | 清单文件包含时间、来源、摘要、版本 |
| 7 | 打包加密、写离机副本 | 加密归档生成；离机副本落盘 |
| 8 | 恢复运行 | 控制面启动正常、节点重连正常 |
| 9 | 记录 | 备份记录已填写（附录 B） |

> 若任一步失败，按 §4.10 处理并**不要**声称备份成功。

### 4.1 步骤 1：准备

```bash
# 示例（通用工具，非产品命令）
df -h <MEDIA>                 # 确认介质已挂载且空间充足
test -w <MEDIA> && echo "media ok"
```

同时确认维护窗口内无人操作：UI 上无正在运行的 Deployment，无进行中的 reconcile，无正在进行的机器添加/删除。

### 4.2 步骤 2：停止变更与停止控制面

**必须先停止控制面**——这是本方案"一致"的来源。

```bash
# 示例（通用工具，非产品命令）
pgrep -af agent-fleet-server        # 确认进程与 PID
# 用你既有的服务管理方式停止控制面（systemd user / launchd / 前台进程），例如：
#   systemctl --user stop agent-fleet-server
pgrep -af agent-fleet-server || echo "server stopped"
```

**待实现验证**：控制面是否提供"优雅停机/暂停写入"的官方方式，需按实现确认；本手册在未确认前一律采用**停止进程**这一最保守做法。

### 4.3 步骤 3：确认无并发写

```bash
# 示例（通用工具，非产品命令）
lsof <DATA_DIR>/fleet.db 2>/dev/null || echo "no holder"
ls -la <DATA_DIR>/fleet.db*
```

- 若存在 `fleet.db-wal` / `fleet.db-shm` 且非空：**完整复制这三个文件**（`fleet.db`、`-wal`、`-shm`），不要只取主库。
- 或者，在确认无进程持有后，用 SQLite 官方方式把 WAL 合并进主库：

```bash
# 示例（SQLite 官方工具，非产品命令）；仅在确认无进程持有后执行
sqlite3 <DATA_DIR>/fleet.db "PRAGMA wal_checkpoint(TRUNCATE);"
sqlite3 <DATA_DIR>/fleet.db "PRAGMA integrity_check;"   # 期望输出 ok
```

然后仍建议连同 `-wal`/`-shm` 一起取（若它们仍存在）。

**停止条件**：若无法确认"无进程在写"，**停止备份流程**，回到步骤 2；不要在生产库上强行复制。

### 4.4 步骤 4：复制材料

```bash
# 示例（通用工具，非产品命令）
mkdir -p <STAGE>/backup-<STAMP>/{pki,config,db,artifacts}

cp -a <DATA_DIR>/pki/ca.key       <STAGE>/backup-<STAMP>/pki/
cp -a <DATA_DIR>/pki/ca.crt       <STAGE>/backup-<STAMP>/pki/
cp -a <DATA_DIR>/pki/server.key   <STAGE>/backup-<STAMP>/pki/
cp -a <DATA_DIR>/pki/server.crt   <STAGE>/backup-<STAMP>/pki/
cp -a <CONFIG_DIR>/config.yaml    <STAGE>/backup-<STAMP>/config/
cp -a <DATA_DIR>/fleet.db         <STAGE>/backup-<STAMP>/db/
cp -a <DATA_DIR>/fleet.db-wal     <STAGE>/backup-<STAMP>/db/ 2>/dev/null || true
cp -a <DATA_DIR>/fleet.db-shm     <STAGE>/backup-<STAMP>/db/ 2>/dev/null || true

# 仅在恢复目标包含"恢复后可直接 reconcile"时才需要：
cp -a <DATA_DIR>/artifacts/skills <STAGE>/backup-<STAMP>/artifacts/
cp -a <DATA_DIR>/artifacts/agentd <STAGE>/backup-<STAMP>/artifacts/
```

### 4.5 步骤 5：校验

**(a) 摘要**

```bash
# 示例（Linux）
cd <STAGE>/backup-<STAMP> && sha256sum $(find . -type f ! -name 'manifest.sha256' | sort) | tee manifest.sha256
# macOS：find . -type f ! -name 'manifest.sha256' | sort | xargs shasum -a 256 | tee manifest.sha256
```

**(b) CA 与私钥配对**（键型无关的做法：比较公钥）

```bash
# 示例（openssl 官方工具，非产品命令）
diff <(openssl x509 -in <STAGE>/backup-<STAMP>/pki/ca.crt -noout -pubkey) \
     <(openssl pkey -in <STAGE>/backup-<STAMP>/pki/ca.key -pubout) && echo "ca pair OK"
diff <(openssl x509 -in <STAGE>/backup-<STAMP>/pki/server.crt -noout -pubkey) \
     <(openssl pkey -in <STAGE>/backup-<STAMP>/pki/server.key -pubout) && echo "server pair OK"
```

> RSA 密钥也可用 `openssl x509 -noout -modulus` 与 `openssl rsa -noout -modulus` 比较；上面用公钥比较的方式对 EC 同样适用。

**(c) 服务端证书由本 CA 签发**

```bash
# 示例（openssl 官方工具，非产品命令）
openssl verify -CAfile <STAGE>/backup-<STAMP>/pki/ca.crt <STAGE>/backup-<STAMP>/pki/server.crt
```

**(d) 权限**

```bash
# 示例（通用工具，非产品命令）：私钥应为 600
stat -c '%a %n' <STAGE>/backup-<STAMP>/pki/*.key 2>/dev/null \
  || stat -f '%Lp %N' <STAGE>/backup-<STAMP>/pki/*.key     # macOS
```

**(e) 数据库完整性**

```bash
# 示例（SQLite 官方工具，非产品命令）
sqlite3 <STAGE>/backup-<STAMP>/db/fleet.db "PRAGMA integrity_check;"   # 期望 ok
sqlite3 <STAGE>/backup-<STAMP>/db/fleet.db "SELECT count(*) FROM machines;"
sqlite3 <STAGE>/backup-<STAMP>/db/fleet.db "SELECT count(*) FROM agent_certificates;"
```

**失败即停止**：任一项不符（配对失败、verify 失败、integrity_check 非 ok、私钥权限非 600），按 §4.10 处理——不要带着"应该没事"进入打包。

### 4.6 步骤 6：备份清单与元数据

在备份目录内生成一份清单（模板见附录 B），至少记录：

- 备份时间（UTC）、控制面主机名、执行者；
- 控制面版本（**待实现确认**：控制面是否暴露 `--version` 或等价版本标识；若无，记录部署来源与提交号）与数据库迁移版本（`migrations/` 已应用到第几号）；
- 每个文件的 SHA-256；
- 本次是否包含 `artifacts/`（即恢复目标）；
- 已知差异备注。

### 4.7 步骤 7：打包、加密与离机副本

```bash
# 示例（通用工具，非产品命令）
tar -czf <STAGE>/ca-backup-<STAMP>.tar.gz -C <STAGE>/backup-<STAMP> .

# 加密（三种任选其一，按你既有做法；下面以 gpg 对称加密为例）
gpg --symmetric --cipher-algo AES256 \
    --output <MEDIA>/ca-backup-<HOST>-<STAMP>.tar.gz.gpg \
    <STAGE>/ca-backup-<STAMP>.tar.gz

# 校验密文本身可解密且与明文一致（解密到管道，不落盘）
gpg --decrypt <MEDIA>/ca-backup-<HOST>-<STAMP>.tar.gz.gpg | sha256sum
sha256sum <STAGE>/ca-backup-<STAMP>.tar.gz        # 两者应一致

# 清理本机明文暂存
shred -u <STAGE>/ca-backup-<STAMP>.tar.gz 2>/dev/null || rm -f <STAGE>/ca-backup-<STAMP>.tar.gz
rm -rf <STAGE>/backup-<STAMP>
```

- **离机副本**：把 `<MEDIA>/ca-backup-<HOST>-<STAMP>.tar.gz.gpg` 复制到至少**第二处**离线介质（与主介质不同物理位置/不同设备）。
- **口令**：加密口令**不得**与介质放在一起，也不得写入清单文件（附录 B 的模板不含口令字段）。
- **顺带校验**：确认离机副本的大小/摘要与主副本一致。

### 4.8 步骤 8：恢复运行

```bash
# 示例（通用工具，非产品命令）
# 用你既有的服务管理方式启动控制面
#   systemctl --user start agent-fleet-server
```

**启动后验证**：

1. 控制面进程存活、Web/API 可访问；
2. 至少一台已知节点重新建立 mTLS `Connect` 流，且 `AgentConnected=True`；
3. 未出现证书相关错误（如 `CertificateExpired`、TLS 握手失败）；
4. 无未决操作异常堆积。

### 4.9 备份完成判据

- [ ] 步骤 5 全部校验通过；
- [ ] 加密归档生成，且"解密后摘要 = 明文摘要"验证通过；
- [ ] 离机副本已写，且摘要一致；
- [ ] 本机明文暂存已清理；
- [ ] 备份记录（附录 B）已填写并归档到**受控位置**（不含口令、不含私钥）。

### 4.10 常见失败与处理

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `lsof` 显示进程仍持有 `fleet.db` | 控制面未真正停止，或另有进程 | 回到步骤 2，确认进程退出；不要强行复制 |
| `wal_checkpoint` 报库忙 | 仍有写进程 | 停止流程，排查持库进程 |
| `integrity_check` 非 `ok` | 磁盘损坏 / 复制时库在写 | **停止**，不要用该副本；排查磁盘，必要时从更早的可用备份恢复 |
| CA 配对检查失败 | `ca.crt` 与 `ca.key` 不同源（曾替换过其中之一） | **停止**；先查清哪一份是正确的信任锚，再重建备份 |
| `openssl verify` 失败 | `server.crt` 非本 CA 签发 | **停止**；确认服务端证书来源 |
| 私钥权限不是 600 | 复制时未保留权限 | 修正权限后重做校验；若介质本身不受控，视为介质不合格 |
| 无法解密归档 | 口令错 / 归档截断 | 视为**无可用备份**，按 §6.3 分支二评估；同时修复备份流程 |

### 4.11 关于在线备份（不推荐，须自证）

MVP 不提供在线备份接口，也不保证"暂停写"由产品自动完成。若你选择 `sqlite3 .backup` 或文件系统快照等在线方式：

- 你必须自行提供其**一致性与可用性的真实依据**（例如在隔离环境实际恢复到可用状态），并自行承担验证责任；
- 在线备份**不能替代**本文的离线方案作为"最后可依赖的备份"；
- 无论用哪种方式，恢复前检查（§6.1）与演练（§7）都不可省略。

## 5. 敏感材料保护（对应架构 §4.6 第 5 条）

### 5.1 介质与口令

- 备份必须落在**操作者控制的加密介质或加密存储**内（加密卷、加密归档均可）。
- **介质与解密口令分开保管**：不同物理位置、不同保管方式；不要写在标签、便签、清单文件或密码管理器之外的任何明文位置。
- 建议至少两份离机副本，且不要放在同一故障域（同一台机器、同一云盘账户）。

### 5.2 权限

- 还原出的私钥必须为 `0600`；备份目录整体只对操作者本人可读。
- 若介质支持访问控制（如文件系统权限/共享口令），一并启用。

### 5.3 保留与可恢复性检查

- 保留策略由你自定，但**必须**保留"当前 CA 有效期内至少一份可恢复副本"，并在 CA 材料变更后更新。
- **定期可恢复性抽查**：至少每 90 天，用一份副本在**隔离环境**实际走一次 §6.5 的隔离恢复检查 + §7 演练。不做抽查的备份只能算"文件还在"。

### 5.4 禁止事项（红线）

1. 不得把备份文件、CA 私钥、服务端私钥、解密口令**上传任务系统、工单、邮件、聊天、日志、代码仓库或任何第三方服务**（含本项目所在的任务平台）；
2. 不得把私钥内容打印到终端后复制粘贴到任何地方；校验只保留摘要与结论；
3. 不得把备份介质与口令放在同一处；
4. 不得把本手册的示例命令原样执行到未核对路径的生产环境；
5. 不得在多人共享主机上把备份明文留在未加密的 `/tmp` 或家目录。

### 5.5 泄露最小化

- 备份过程中产生的临时文件用完即删；若曾落到未加密磁盘，按你的介质处置流程处理该磁盘。
- 若怀疑备份介质或口令泄露，按 **CA 泄露**处理（§6.4）——**不要**假定"只是备份泄露，没关系"。

## 6. 恢复流程

### 6.0 决策树

```text
CA 私钥是否泄露（或被合理怀疑泄露）？
├─ 是 → 分支三：重建信任（§6.4）。恢复旧备份不能消除泄露。
└─ 否 → CA 私钥是否丢失/不可用？
        ├─ 是 → 是否有可用备份（能通过 §6.1 检查）？
        │       ├─ 有 → 分支一：恢复备份（§6.2）
        │       └─ 无 → 分支二：重新生成 CA + 全机群重新 bootstrap（§6.3）
        └─ 否 → 不需要 CA 恢复；若只是控制面主机故障，仍按分支一恢复以保证"CA 与库成套"
```

### 6.1 恢复前检查（任一项不满足即**停止恢复**，保留原现场）

| # | 检查项 | 判据 | 不满足时 |
|---|---|---|---|
| 1 | 事件分类 | 已确认属于"丢失"还是"泄露"（泄露直接转 §6.4，不走本表） | 停止，先分类 |
| 2 | 备份来源可信 | 介质、时间、清单（附录 B）、校验值可追溯 | 停止，不要用来源不明的副本 |
| 3 | 归档可解密/可展开 | 解密成功，`manifest.sha256` 逐项通过 | 视为无可用备份 → §6.3 |
| 4 | 版本/配置兼容 | 备份生成的控制面版本与迁移版本**可从当前目标版本顺序应用**；不跳版本、不倒序 | 停止，先在隔离环境验证迁移路径 |
| 5 | CA 与证书配对 | `ca.key` 与 `ca.crt` 公钥一致；`server.crt` 由该 CA 签发 | 停止，先查清正确材料 |
| 6 | 数据一致性 | `fleet.db` 可打开、`integrity_check=ok`、迁移可应用 | 视为无可用备份 → §6.3 |
| 7 | 身份元数据对应 | `machines`、`agent_certificates` 与恢复目标机群一致（机器数与预期相符） | 停止，确认是否拿错备份 |
| 8 | 权限可还原 | 私钥可还原为 0600，属主正确 | 停止，先修介质/权限 |
| 9 | **隔离位置** | 目标恢复位置为隔离目录/隔离主机，未直接覆盖线上 | 先建隔离位置 |
| 10 | **退回路径** | 已保有当前（失败）现场的可回退副本 | 先做现场副本，再继续 |

### 6.2 分支一：CA 丢失，但有可用备份

**目标**：在不重新 enroll 全部节点的前提下，恢复信任根与控制面身份对应。

**步骤**

1. 完成 §6.1 全部检查。
2. **先在隔离位置还原**（§6.5）并验证通过；不要直接覆盖线上。
3. 保存当前失败现场（先把现有 `<DATA_DIR>`、`<CONFIG_DIR>` 整体复制到 `<MEDIA>/pre-restore-<STAMP>/` 作为退回路径）。
4. 停止控制面。
5. 还原材料：`pki/`（ca.key/ca.crt/server.key/server.crt）、`config.yaml`、`fleet.db`（及 `-wal`/`-shm` 一致性处理）；若恢复目标需要，还原 `artifacts/`。
6. 修正权限：私钥 0600，属主为运行控制面的用户。
7. 启动控制面，检查迁移是否按序应用成功。
8. 执行 §6.7 恢复后验证。

**预期结果（设计预期，未验证）**：既有节点凭原 `client.crt/key` 直接建立 mTLS `Connect` 流，无需重新 enroll；machineId 与库中记录一致。

**注意**：恢复旧备份**只恢复可用性**。若本次丢失伴随"备份曾落入他人之手"的可能，则按 **泄露**处理（§6.4）。

### 6.3 分支二：CA 丢失，且无可用备份

**目标**：重建信任。这是**最后手段**，代价是全机群重新 enroll。

**步骤**

1. 明确告知影响范围：所有既有客户端证书作废；每台节点需经 SSH 重新 bootstrap。
2. **停止**控制面，保全原有现场（作为退回路径）。
3. 生成**新的 CA**（按实现确认的官方方式；若无官方方式，**待实现验证**，不要凭猜测手工替换 `pki/` 内容）。
4. 决定服务端证书：随新 CA 重新签发（推荐），或沿用旧 `server.crt`（此时需确认客户端信任锚仍包含旧证书链——**待实现验证**）。
5. 重置控制面中与证书相关的身份元数据（`agent_certificates` 中旧序列号的处置），保留 `machines` 记录以复用 machineId ↔ SSH alias 映射（**待实现验证**：控制面是否支持"保留机器记录、重签证书"的路径；若不支持，需按实现确认的删除/重建流程操作）。
6. 启动控制面，逐台经 SSH `repair` 让节点重新 enroll（新 token + 新 CSR，按架构 §7.5 时序）。
7. 每台节点验证：`AgentConnected=True`，machineId 与库中记录一致。
8. 按 §6.7 验证，并**立即**为新 CA 建立备份（回到 §4）。
9. 记录本次事件与重建范围（附录 A 的事件记录区）。

**预期结果**：全机群以新信任根恢复管理能力；旧证书不再被接受。

### 6.4 分支三：CA 泄露

> **核心原则：恢复旧备份不能消除已经泄露的信任。**

泄露意味着攻击者持有的私钥/证书在有效期内仍可能被用于伪造节点或冒充控制面；恢复一份"泄露前"的备份，只是把**已知已被泄露的同一把私钥**再装回去。

**步骤**

1. **立即**假定信任已失效：
   - 停止向外提供服务（必要时停止控制面），避免继续用泄露的信任根接受连接；
   - 若 `server.key` 同时泄露，立即停止使用该服务端证书。
2. 判定泄露窗口（私钥最后一次可信使用时间 → 发现时间），据此评估哪些节点/凭据可能受影响。
3. **重新生成 CA**（新私钥，不复用任何旧材料），重新签发服务端证书。
4. 重新 enroll 全部节点（流程同 §6.3 第 3～7 步）。
5. 视泄露范围处置其它凭据：
   - admin token（若与备份同处泄露）；
   - 备份介质与口令本身（视为已泄，全部更换）；
   - 受影响机器的记录与审计（保留事实，不要静默删除）。
6. **不得**把已泄露私钥作为"恢复"重新启用；**不得**用"恢复备份"替代重建。
7. 记录事件：泄露时间窗、重建范围、处置动作、遗留判断，并按需评估是否通报。
8. 重建完成后**立即**对新 CA 建立并演练备份。

**预期结果**：信任根系全部更换；旧私钥/旧证书不再被接受；事件有完整记录。

### 6.5 隔离恢复位置的先行验证

在覆盖线上之前，先把备份还原到隔离位置（隔离主机或隔离目录 + 不同端口），验证：

1. 控制面能启动、迁移能应用、Web/API 可访问；
2. `fleet.db` 可查询（机器数、证书数符合预期）；
3. 用**恢复后的 CA 与既有节点材料**能通过校验路径（在隔离环境用 `openssl verify` 验证既有 `client.crt`，或在隔离控制面上让一台测试节点连接）；
4. 用**不属于该 CA** 的证书 / **已过期**证书验证会被拒绝；
5. 记录隔离验证结果（附录 C）。

隔离环境**不得**连生产网络，避免隔离实例影响真实节点。

### 6.6 覆盖线上与退回路径

- 覆盖前必须已保存失败现场（§6.2 第 3 步）。
- 覆盖过程中出现任何异常：**停止**，回退到失败现场，如实报告；**不得**"边猜边改"。
- 退回后系统可能仍不可用，但必须保持在**可解释状态**：明确当前是"原现场"还是"已恢复副本"，不要混用两套材料。

### 6.7 恢复后验证

- [ ] 控制面进程正常，无迁移错误；
- [ ] 至少一台已知可信节点建立 mTLS `Connect` 流，machineId 与库中一致；
- [ ] 用不属于该 CA 的证书连接 → 被拒绝；
- [ ] 用已过期证书连接 → 被拒绝（若可构造，见 §7 DR-4）；
- [ ] 关键资源可读：配置、`machines`、`agent_certificates`、（按恢复目标）工件；
- [ ] 无异常未决操作堆积；
- [ ] 恢复记录（附录 A）已填写。

### 6.8 失败停止条件汇总

| 条件 | 动作 |
|---|---|
| 归属分类不清（丢失 vs 泄露） | 停止，先分类 |
| 备份无法解密/展开/摘要不符 | 视为无可用备份，转分支二 |
| CA 配对失败 / 服务端证书链不符 | 停止，查清材料来源 |
| 数据库 `integrity_check` 非 ok | 停止，禁用该副本 |
| 版本/迁移不可顺序应用 | 停止，隔离环境验证迁移路径后再继续 |
| 权限无法还原为 0600 | 停止，先修介质 |
| 无退回路径 | 停止，先做现场副本 |
| 恢复后既有节点无法连接（分支一） | 停止，**不得**降级为"直接重新 enroll"来自行掩盖；先查清是恢复不完整还是材料不符，记录后按分支二重新决策 |

## 7. 演练计划（DR-1～DR-8）

### 7.1 目的与性质

备份存在**不等于**可恢复。演练用一份**测试用**材料，在隔离环境证明"恢复流程真的能跑通"，并把失败点暴露在真正灾难之前。

> **当前状态：计划已定义、未执行。** 本节的"成功判据"是验收标准，不是已通过的结果。

### 7.2 环境要求

- **隔离测试环境**：独立主机或隔离目录 + 独立端口；不接生产网络；建议用假的/测试用 CA 材料，**不要**用生产 CA（见 §7.5）。
- 至少一台**测试节点**（可用容器/临时 HOME 模拟），用于连接与拒绝验证。
- 通用工具齐备（`openssl`、`sqlite3`、`tar`、`sha256sum`）。

### 7.3 演练项

| # | 演练项 | 步骤要点 | 成功判据 |
|---|---|---|---|
| DR-1 | 归档完整性/权限检查 | 解密归档；展开；核对摘要；检查私钥权限；验证 CA 配对 | 摘要逐项一致；私钥 0600；公钥配对不同则失败 |
| DR-2 | 隔离环境控制面启动 | 用备份在隔离位置启动控制面 | 进程正常；迁移顺序应用成功；`fleet.db` 可打开且 `integrity_check=ok` |
| DR-3 | 可信节点连接 | 让测试节点用既有客户端证书连接隔离控制面 | mTLS `Connect` 建立；machineId 与库中记录一致 |
| DR-4 | 错误/过期证书被拒绝 | 分别用"非本 CA 签发"与"已过期"的客户端证书连接 | 两种都被拒绝；失败可观测（日志/事件中有记录） |
| DR-5 | 关键资源恢复 | 恢复后读取配置、`machines`、`agent_certificates`、按目标的工件 | 内容与语义符合预期；无缺列/缺文件 |
| DR-6 | CA 丢失（有备份）路径 | 按 §6.2 完整走一遍（隔离环境） | 既有测试节点无需重新 enroll 即可连接 |
| DR-7 | CA 丢失（无备份）路径 | 按 §6.3 完整走一遍（隔离环境） | 新 CA 生效；测试节点经重新 enroll 后连接成功；旧证书被拒绝 |
| DR-8 | 异常恢复路径 | 注入一种异常：备份损坏 / 配对失败 / 迁移失败 | 流程在预定停止点**停止并保留原现场**、按退回路径回退；无静默覆盖 |

### 7.4 频率与范围

- 建议：**每 90 天**至少做 DR-1～DR-3；**每 180 天**做一次含 DR-6/DR-7 的完整演练。
- CA 变更、控制面大版本升级、备份介质更换后，应重做一次完整演练。
- 演练结果必须填写附录 A，并归档到受控位置。

### 7.5 演练的安全边界

- **默认使用测试用 CA 材料**，避免把生产信任根复制到隔离环境。若必须用生产材料演练，则隔离环境的安全等级不得低于生产（加密介质、访问控制、离机存放），并在演练后按泄露风险评估是否需要轮换。
- 演练记录**不得**包含私钥、口令或可解密内容；只记录步骤、判据、结论与失败点。
- 演练中生成的一切临时私钥材料，演练结束即销毁。

### 7.6 记录与证据

- 每次演练一份记录（附录 A），包含：日期、执行者、环境、DR 项、每项判据结果、发现的失败与修复、结论（通过/不通过/部分）。
- **不通过**的演练必须挂待办并复演；在通过之前，"CA 可恢复"不得作为对外结论。

## 附录 D：命令与占位符说明

- 本手册所有命令均为**通用系统工具示例**（`tar`、`openssl`、`sqlite3`、`sha256sum`/`shasum`、`gpg`、`stat`、`lsof`、`pgrep`），**不是 agent-fleet 产品接口**。执行前请按你的实际部署替换占位符并与运维规范核对。
- 标注 **待实现验证** 的步骤，表示产品行为尚未在实现中确认，**不得**凭猜测执行；确认前只能作为步骤描述保留。
- `<...>` 为占位符，不要原样执行；尤其 `<MEDIA>`、`<DATA_DIR>`、`<CONFIG_DIR>`、`<STAGE>`、`<STAMP>`、`<HOST>`。
- 命令输出中若可能包含私钥或口令，**不要**粘贴到任何平台；只记录摘要与结论。
